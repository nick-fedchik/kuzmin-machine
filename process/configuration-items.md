# Реєстр елементів конфігурації

* **Версія:** 0.1.0 (чернетка для рішення власника)
* **Дата:** 2026-11-12
* **Власник проєкту:** Микола Мартинович Федчик
* **Призначення:** визначити конкретні результати й критичні документи,
  зміни яких важливо контролювати разом із пов'язаними результатами.

Це не інвентар усіх файлів: Git версіонує й матеріали поза реєстром.
[Словник Work Products](../docs/governance/work-products.md) описує типи,
а цей реєстр — **обрані конкретні WP** або явно визначені групи WP.
Включення не означає затвердження змісту, завершення роботи чи незалежної
перевірки. Склад є пропозицією для рішення власника.

## 1. Відбір і властивості

Кандидат є CI, якщо його зміна може істотно вплинути на узгоджені правила,
інтерфейси, реалізацію, відтворення важливого результату або рішення
про стан проєкту. Групу використовують, коли її конкретно перелічені
частини потрібно контролювати як одиницю.

Для кожного CI наведено ідентифікатор, тип WP, шлях, стан і орієнтир
ASPICE. **Відповідального за супровід окремих CI ще не визначено**;
власник проєкту вирішує склад реєстру й призначення відповідальних.
Точну версію кожного Git-об'єкта визначають через коміт або тег обраної
базової конфігурації, а не через поточний вміст гілки.

інформаційних елементів**, а не вимогу мати файл саме з такою назвою чи

сам є кандидатом для `01-52 Configuration item list` у `SUP.8`; критерії
відбору відповідають призначенню `18-53 Configuration item selection
criteria`. Застосовність процесів і повнота кожного WP окремо не оцінені.

## 3. Базова конфігурація та зміни

Сам реєстр **не є базовою конфігурацією**. Для конкретного прототипу,
експерименту чи випуску визначають потрібний склад CI та фіксують стан
доступним комітом або тегом Git; якщо потрібні зовнішні дані, інструменти,
бітстрім чи фізична плата — окремо зазначають їхній ідентифікатор,
версію/контрольну суму й місце зберігання, якщо відомі. Не вважають
поточну гілку або історичний тег автоматично узгодженою базою MVP.

Оновлюючи CI, перевіряють пов'язані вимоги, код і результати та зазначають
суттєві розбіжності; зміни погоджують за чинними правилами проєкту.
Перелік CI, їхній стан та призначення відповідальних переглядає власник.

## Джерело та межі ASPICE

[Automotive SPICE PAM 4.0, VDA QMC](https://vda-qmc.de/wp-content/uploads/2023/12/Automotive-SPICE-PAM-v40.pdf),
зокрема `SUP.8` (стор. 81–82), відповідні процеси розроблення та Annex B.
`SUP.8.BP1` стосується вибору й ідентифікації CI, `BP2` — їхніх
властивостей, `BP5` — базових конфігурацій. Інформаційні елементи в PAM —
приклади інформації та її характеристик, які організація може представляти
різними способами; це не перелік обов'язкових окремих файлів.

ASPICE тут — інженерний орієнтир, не зовнішня вимога. Наявність запису,
файлу чи посилання не підтверджує виконання процесу або відповідності
моделі. Див. [позицію проєкту щодо стандартів](standards-position.md).

| Термін | Значення |
|---|---|

| PAM | Process Assessment Model, модель оцінювання процесів |
| BP | Base Practice, базова практика |
