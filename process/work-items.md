# Каталог Work Items НДДКР

* **Версія:** 0.1.0 (проєктна угода)
* **Дата:** 2026-11-12
* **Призначення:** узгодити види відстежуваної роботи та питань без зайвих Issue.

Work Item — одиниця роботи або питання, яке потрібно відстежувати.
[Work Product](../docs/governance/work-products.md) — результат чи збережений
матеріал: висновок, дані, рішення, код, специфікація тощо. GitHub Issue —
запис для відстеження Work Item; не кожній дії потрібна окрема Issue і не
кожна Issue створює окремий файл або WP.

## 1. Види роботи

| Вид | Призначення | Очікуваний результат | Мітка Issue |
|---|---|---|---|
| `Research` | Дослідити питання чи джерела | Обґрунтований висновок із межами; негативний чи невизначений результат допустимий | `type:research` |
| `Experiment` | Виконати конкретну перевірку чи вимірювання | Дані й висновок щодо питання | `type:experiment` |
| `Task` | Розробити, змінити або перевірити результат | Код, прототип, рішення, специфікація, результат перевірки або інший конкретний результат | `type:task` |
| `Finding` | Зафіксувати знахідку чи дефект | Опис проблеми та її обставин для подальшого вирішення | `type:finding` |
| `Change Request` (`CR`) | Розглянути запропоновану зміну узгодженого результату чи меж | Рішення прийняти, відхилити чи відкласти зміну; за потреби — план реалізації | `type:change-request` |
| `Risk` | Відстежити можливу несприятливу подію | Оцінка ризику та рішення щодо реагування | `type:risk` |

Перевірка може бути `Task` або `Experiment`: вибір залежить від питання
й характеру роботи. Види та мітки — домовленість проєкту, а не класифікація,
нав'язана GitHub або стандартом.

## 2. Ознаки та стан

- `type:*` показує вид; `area:theory`, `area:hw`, `area:sw`, `area:sys`
  та `area:process` — область.
- Пріоритет (`priority:*`), важливість знахідки (`sev:*`), мітки `ready`,
  `blocked`, `accepted` і стан у GitHub Project — окремі ознаки. Назва
  мітки `ready` не тотожна автоматично стану Project `Ready`.
- Мітки `aspice:*` застосовують за потреби до відповідної роботи, а не
  вимагають для кожного дослідження.

Поточні поля Project та правила закриття `Finding` і `Risk` визначені в
[настанові проєкту, §6](PROJECT-MANUAL.md#6-github-issues-і-project).

## 3. Ієрархія і зв'язки

Issue може бути батьківською або дочірньою залежно від зв'язку
Parent Issue / Sub-Issue. Окремий тип або мітка `Epic` не потрібні:
масштаб видно з мети та зв'язків. `Experiment` може охоплювати кілька
результатів або бути атомарною Issue.

Типові, але необов'язкові зв'язки:

- `Research` може породити `Experiment`, а `Experiment` — `Task` для
  підготовки, реалізації або аналізу. Дослідження може завершитися і без
  експерименту.
- `Experiment` може виявити `Finding` або дати підставу для `CR`; не кожен
  результат потребує окремої Issue.
- `Finding` може привести до `CR` або `Risk`; оцінка `Risk` може привести
  до `Task` реагування. Не кожна знахідка створює ризик, а ризик може
  виникнути без попередньої знахідки.

Причинний зв'язок, декомпозиція Parent / Sub-Issue та блокувальна залежність
різні; ці приклади не нав'язують конкретної ієрархії. Дочірню Issue
створюй, коли є сенс окремо відстежувати її результат; дрібні кроки можна
залишити чеклістом.

Атомарна задача має один основний результат, зрозумілі межі та спосіб
перевірити завершення. Це практична домовленість, а не окремий тип GitHub.
Сама атомарність не визначає тривалості, кількості PR чи числової метрики;
чинні правила виконання і WIP — у [настанові](PROJECT-MANUAL.md).

## 4. CR і Task

`CR` потрібен, коли треба вирішити, чи і як змінювати узгоджену вимогу,
специфікацію, архітектуру або межі проєкту. Прийняття пропозиції саме
по собі не означає, що зміну реалізовано.

`Task` — робота для отримання конкретного результату; вона також може
змінювати документи або код. Після прийняття `CR` окрема `Task` може
реалізувати рішення. Для очевидної правки в межах повноважень виконавця
окремий `CR` не потрібен.

Наприклад, змінити узгоджене правило семантики KPOL — `CR`, якщо спочатку
потрібно погодити правило й наслідки; оновити парсер і тести після такого
рішення — `Task`. Виправлення описки без зміни змісту — зазвичай `Task`.
