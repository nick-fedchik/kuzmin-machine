## 1. Межі

- ASPICE — модель оцінювання процесів для автомобільної галузі. Зовнішньої вимоги до проєкту немає ([позиція щодо стандартів](standards-position.md)). ASPICE тут — **перелік добрих практик**, а не мета сертифікації.
- **Ціль:** для обраних процесів досягти того, що ASPICE називає рівнем можливостей 1 («Performed process»): результати процесу реально існують. Рівні 2+ (керування виконанням і робочими продуктами) — не зараз.
- **Що не робимо:** формальне оцінювання, інструменти класу DOORS / Polarion, процеси MLE.x, SUP.11, ACQ.4, SPL.2, REU.2, PIM.3.
- **Поточний стан** (перевірено в `origin/main` 2026-11-09): 1 тег git (`v0.4.0` на `c1b9d2f`); 30 вимог `REQ-*` у `requirements/requirements.md` 0.1.0 (перенесено з `drafts` без рецензії, перевірка — S2); його матриця простежуваності посилається на шляхи старої структури, тож робочого трасування (К4) ще немає; запити на зміни ведуться через Issues (`type:change-request`, #29, #46). Рецензування налагоджено ([правила](review-rules.md)).

## 3. Порядок і залежності

1. **Відразу, без ризику конфліктів:** К1, К2, К5, К6.
2. **Потім:** К3 → К4 (трасування неможливе без реєстру вимог).
3. **Після появи реєстру:** К7.
4. **Наприкінці:** К8, К9.

Узгодження з Gemini: його гілка `audit/kpol-v0.2-v0.9-report` змінює `kpol_reference.py` і `test_kpol_reference.py`. Кроки К3/К4 щодо KPOL краще починати після злиття цієї гілки.

## 4. Рішення, потрібні від власника

1. Схема ID вимог: `REQ-SYS/HW/SW-NNN` чи інша.
2. Знахідки — у GitHub Issues чи в окремому файлі-реєстрі (Issues зручніші для статусів; файл — для архіву поруч із документами).
3. Схема тегів базових версій.
4. Чи потрібне підтвердження людиною (вами) для зміни статусу AV-xx на «Прийнято».

## 5. Що це дасть і чого не дасть

- **Дасть:** перевірювані вимоги; видимий зв'язок «вимога → тест → результат»; відтворювані базові версії; закриття знахідок не губиться.
- **Не дасть:** відповідності ASPICE (її встановлює лише формальне оцінювання), ISO 26262 чи будь-якому іншому стандарту.
