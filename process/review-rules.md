## 1. Ролі

| Роль | Хто це | Що створює | Чого не робить |
| :--- | :--- | :--- | :--- |
| **Виконавець** (автор) | Людина або агент, що виконав роботу | **Report** (звіт) або **Specification** (специфікацію) | Не рецензує власний документ |
| **Рецензент** | Перевіряє один документ: чи випливають висновки з даних, чи дотримано плану | **Review Report** | Не редагує чужий документ; знахідки лише записує у Review Report |
| **Аудитор** | Перевіряє кілька документів або відповідність процесу цим правилам і плану | **Review Report** (зведений, див. §4.3) | Те саме |
| **Перевіряльник** | Незалежно відтворює вимірювання чи прогін і порівнює результат | **Review Report** з власними сирими даними | Те саме |

Рецензент, аудитор і перевіряльник — це різновиди однієї ролі. Усі вони пишуть документ одного класу — Review Report.

**Незалежність.** Автор документа не може бути його рецензентом. Якщо рецензент брав участь у створенні предмета перевірки (коду, RTL, плану), він зазначає це в шапці як конфлікт інтересів.

## 2. Класи документів

| Клас | Що це | Приклади | Де лежить |
| :--- | :--- | :--- | :--- |
| **Report** | Запис виконаної роботи та її результатів: експеримент, тест, бенчмарк, HIL-прогін, оцінка | `AV-08_Scaling_Report_UA.md` | `<розділ>/Reports/` |
| **Specification** | Вимоги, архітектура, мова, інтерфейс, методика | `Kuzmin-Machine-KPOL-Language-v0.9-Specification-UA.md` | Корінь розділу (як зараз) |
| **Review Report** | Результат рецензії, аудиту або перевірки одного Report чи однієї Specification | `AV-03_SW_Gate_Decision_Review_Report_UA.md` | `<розділ>/Review_Reports/` |

Плани, промпти для рецензентів, мемо й README — допоміжні документи. Вони не є Report і рецензуються лише за потреби.

Специфікацію рецензують за тим самим принципом, що й звіт: одна Specification — один Review Report.

## 3. Структура папок

```text
<NN-розділ>/
├── <специфікації, плани, код — як раніше>
├── Reports/
│   ├── README.md          # реєстр звітів і їхніх рецензій
│   ├── <ID>_<Назва>_Report_UA.md
│   └── raw/               # сирі дані звітів
└── Review_Reports/
    ├── README.md          # реєстр рецензій
    ├── <ID>_<Назва>_Review_Report_UA.md
    └── raw/               # власні сирі дані рецензента (за потреби)
```

Review Report лежить у тому самому розділі, що й документ, який він рецензує.

## 4. Відповідність 1 : 1 та іменування

### 4.1. Іменування

- **Report:** `<ID>_<Назва>_Report_UA.md`, наприклад `AV-04_Formal_Verification_Report_UA.md`.
- **Review Report для звіту:** та сама основа, але `_Report_UA.md` замінюється на `_Review_Report_UA.md`: `AV-04_Formal_Verification_Review_Report_UA.md`.
- **Review Report для специфікації:** основа імені специфікації без `-UA.md` + `_Review_Report_UA.md`. Наприклад, для `Kuzmin-Machine-KPOL-Language-v0.9-Specification-UA.md` це `Kuzmin-Machine-KPOL-Language-v0.9-Specification_Review_Report_UA.md`.
- Ім'я рецензента у файл не пишемо. Його вказують у шапці.

Отже, за іменем звіту завжди можна знайти його рецензію, і навпаки.

### 4.2. Один документ — один Review Report

- На кожен Report або Specification ведеться **один** Review Report.
- Кілька рецензентів пишуть в одному Review Report окремими розділами: «Рецензія версії 1.0 — рецензент Copilot», «Рецензія версії 1.0 — рецензент Gemini».
- Відповідь автора на знахідки й повторна рецензія — нові розділи в тому самому Review Report, а не нові файли.

### 4.3. Виняток: зведений аудит

Аудит, що охоплює кілька документів одночасно (наприклад, AV-03, AV-04, AV-07 і AV-08), оформлюється одним файлом `<Обсяг>_Audit_Review_Report_UA.md` у `Review_Reports/` того розділу, до якого належить більшість охоплених документів. Реєстр `Review_Reports/README.md` перелічує всі охоплені документи, а кожен охоплений Report після появи аудиту посилається на нього в шапці. Зведений аудит не замінює парних Review Report 1 : 1 — він доповнює їх.

## 5. Версіонування

1. **Версія — всередині документа, а не в імені файлу.** Шапка містить поле `Версія: X.Y`, а наприкінці (перед розділом «Абревіатури та глосарій») є таблиця «Історія версій». Попередні версії доступні в історії git.
2. **Версія Review Report тотожна версії документа, який він рецензує.** Рецензія звіту версії 1.1 має версію 1.1. Коли автор випускає 1.2, рецензент додає розділ «Рецензія версії 1.2» і змінює версію Review Report на 1.2. Попередні розділи рецензії не видаляються.
3. **Зміна версії:** X — зміна висновків, даних або методу; Y — виправлення змісту, що висновків не змінюють. Суто редакційні зміни (глосарій, посилання, перенесення файлу, оформлення) версію не змінюють, але записуються в «Історію версій».
4. **Фіксація.** Review Report указує не лише версію, а й коміт git, на якому прочитано документ.

### 5.1. Обов'язкові поля шапки

| Report / Specification | Review Report |
| :--- | :--- |
| Версія | Версія (= версії рецензованого документа) |
| Дата | Дата |
| Виконавець (автор) | Рецензент, роль (рецензент / аудитор / перевіряльник), конфлікт інтересів |
| Підстава (план, розділ) | Рецензований документ: посилання, версія, коміт |
| Review Report: посилання й статус («не створено», «на рецензії», вердикт) | Вердикт (§6) |

## 6. Цикл рецензування й вердикти

```text
Чернетка → На рецензії → (Потрібні виправлення → нова версія → На рецензії)… → Вердикт
```

| Вердикт | Значення |
| :--- | :--- |
| **Прийнято** | Висновки випливають із даних; відтворено або перевірено за сирими даними |
| **Прийнято з обмеженнями** | Ядро результату коректне; окремі твердження треба звузити |
| **Потрібні виправлення** | Без виправлень приймати не можна; автор випускає нову версію |
| **Не прийнято** | Головні висновки не випливають із даних або дані недостовірні |
| **Не перевірено** | Немає можливості перевірити; причина вказана |

Знахідки нумеруються в межах Review Report (З1, З2, …) і мають рівень серйозності: **критична**, **суттєва**, **незначна**.

Статус експерименту чи компонента в планах, беклозі, досьє й матриці TRL змінюється лише після вердикту «Прийнято» або «Прийнято з обмеженнями».

## 7. Git

1. Автор комітить лише свої Report, сирі дані й скрипти. Рецензент комітить лише свій Review Report і його сирі дані.
2. Рецензент не править чужий документ, навіть для «дрібних» виправлень.
3. Префікси повідомлень: `AV-NN:` — звіт експерименту; `AV-NN-REVIEW:` — рецензія; `AV-AUDIT:` — зведений аудит; `docs:` — допоміжні документи.

## 9. Звідки походять ці вимоги

Правило «один звіт — одна рецензія з тією самою версією» в такому вигляді — **конвенція цього проєкту**. Жоден стандарт не вимагає саме такої схеми іменування й папок. Але її складники запозичено з таких джерел:

| Джерело | Що звідти взято | Як перевірено |
| :--- | :--- | :--- |
| **Automotive SPICE 4.0** (VDA QMC, 2023), **SUP.1 Quality Assurance** | BP1: забезпечення якості виконується незалежно й об'єктивно, без конфлікту інтересів; приміткою прямо виключено самоконтроль («no self-monitoring»). BP3: оцінювати робочі продукти за визначеними критеріями й документувати результат. BP6–BP7: невідповідності відстежувати й ескалювати | Звірено з текстом PAM 4.0 |
| ASPICE 4.0, інформаційні елементи **13-19 Review evidence** і **13-25 Verification results** | Зміст Review Report: що перевірено, хто рецензенти, критерії, знахідки (невідповідності й пропозиції), статус. Результати перевірок: пройдено / не пройдено / не виконано з обґрунтуванням, дата, об'єкт | Звірено з текстом PAM 4.0 |
| ASPICE 4.0, **SUP.8 Configuration Management**, **SUP.9 Problem Resolution Management** | Версіонування й фіксація конкретного стану документа; відстеження знахідок до закриття | Назви процесів звірено; деталі — за загальним змістом |
| **Automotive SPICE 3.1** (2017): **SUP.2 Verification**, **SUP.4 Joint Review** | Окремі процеси верифікації та спільного перегляду робочих продуктів. У 4.0 цих процесів уже немає; перевірку описано в самих інженерних процесах (SYS.4–5, SWE.4–6, HWE.3–4) | Відсутність у 4.0 і назви процесів 4.0 звірено з PAM 4.0; зміст 3.1 — з пам'яті |
| **ISO 26262:2018** (функційна безпека автомобільних систем), частини 2 і 8 | Заходи підтвердження (confirmation review, audit, assessment) з рівнями незалежності I0–I3; верифікація з окремим звітом про верифікацію | З пам'яті; перед посиланням у зовнішніх документах звірити номери розділів |
| **IEEE 1028-2008** «Software Reviews and Audits» | Типи перевірок (технічна рецензія, інспекція, аудит), ролі (автор, рецензент, аудитор) і вихідний документ кожної перевірки | З пам'яті |
| **DO-178C**, **IEC 61508** | Вимога виконувати частину перевірок «з незалежністю» для критичних рівнів | З пам'яті |
| **ISO 9001:2015** (і військовий **AQAP-2110**, що на ньому базується) | Перегляди й верифікація проєктування (8.3.4), керування документованою інформацією та її версіями (7.5), внутрішній аудит (9.2) | З пам'яті |
| Наукова практика | Попередня реєстрація гіпотез і критеріїв, рецензування, сирі дані й походження | [План експериментів, §2](../experiments/PLAN.md) |

Отже, ASPICE — одне з джерел, а не єдине: з нього взято незалежність QA і зміст запису рецензії. Найсуворіші вимоги до незалежності — в ISO 26262, IEC 61508 і DO-178C. Ролі й типи рецензій найдокладніше описано в IEEE 1028.

Стандарти безпеки (ISO 26262, DO-178C, IEC 61508) тут — лише джерело практик рецензування. Проєкт їм не відповідає й не заявляє цього: див. [позицію щодо стандартів безпеки](standards-position.md). Подальші кроки за ASPICE 4.0 — у [плані кроків](aspice-steps.md).
