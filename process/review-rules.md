## 1. Ролі

| Роль | Хто це | Що створює | Чого не робить |
| :--- | :--- | :--- | :--- |
| **Виконавець** (автор) | Людина або агент, що виконав роботу | **Report** (звіт) за [шаблоном](../docs/templates/report.md) або **Specification** (специфікацію) | Не рецензує власний документ |
| **Рецензент** | Перевіряє один документ: чи випливають висновки з даних, чи дотримано плану | **Review Report** за [шаблоном](../docs/templates/review.md) | Не редагує чужий документ; знахідки лише записує у Review Report |
| **Аудитор** | Перевіряє кілька документів або відповідність процесу цим правилам і плану | **Review Report** (зведений аудит за [методикою](audit/ASPICE-Audit-Method.md)) | Те саме |
| **Перевіряльник** | Незалежно відтворює вимірювання чи прогін і порівнює результат | **Review Report** з власними сирими даними | Те саме |

Рецензент, аудитор і перевіряльник — це різновиди однієї ролі. Усі вони пишуть документ одного класу — Review Report.

**Незалежність.** Автор документа не може бути його рецензентом. Якщо рецензент брав участь у створенні предмета перевірки (коду, RTL, плану), він зазначає це в шапці як конфлікт інтересів.

**Правило вибору рецензента серед ШІ-агентів ([PROJECT-MANUAL §2.1](PROJECT-MANUAL.md#21-агенти-проєкту)):**
Незалежність визначає родина моделей, а не інструмент. Рецензент обов'язково має належати до **іншої родини моделей**, ніж виконавець (автор):
- на роботу моделей родини Claude (Claude Code, GitHub Copilot з моделлю Claude) рецензентом призначається модель родини Gemini (Gemini CLI / Antigravity), і навпаки;
- OpenCode або Copilot підходять для рецензування за умови вибору моделі іншої родини;
- аудитор за [методикою аудиту](audit/ASPICE-Audit-Method.md) — також модель іншої родини, ніж автори об'єкта аудиту, і обов'язково працює в чистій сесії.

У шапці кожного Report і Review Report обов'язково вказують і агента, і конкретну модель.

Специфікацію рецензують за тим самим принципом, що й звіт: одна Specification — один Review Report.

## 3. Структура розміщення

Нормативна структура репозиторію визначається [PROJECT-MANUAL §5.1](PROJECT-MANUAL.md#51-структура-репозиторію):

```text
kuzmin-machine/
├── docs/
│   └── templates/         # шаблони Report, Review Report та інших WP
├── requirements/
│   └── requirements.md    # вимоги та матриця трасування
├── architecture/
│   ├── refactoring-plan.md
│   └── software/
├── specs/
│   └── kpol/
│       ├── README.md      # реєстр версій специфікації KPOL
│       ├── kpol-X.Y.Z.md  # специфікація мови
│       └── reviews/       # рецензії на специфікації
├── experiments/
│   ├── PLAN.md            # чинний план експериментів
│   └── AV-xx/
│       ├── report.md      # звіт за шаблоном docs/templates/report.md
│       ├── review.md      # рецензія за шаблоном docs/templates/review.md
│       ├── scripts/       # скрипти відтворення експерименту
│       └── raw/           # незмінні сирі дані експерименту
└── process/
    ├── PROJECT-MANUAL.md  # настанова проєкту
    ├── review-rules.md    # ці правила
    └── audit/
        ├── ASPICE-Audit-Method.md
        └── reports/       # звіти зведеного аудиту
```

Для експериментів парні документи `report.md` і `review.md` розташовуються в одному підкаталозі експерименту `experiments/AV-xx/`. Для специфікацій KPOL рецензії зберігаються у `specs/kpol/reviews/`. Для міграційних і процесних перевірок рецензія зберігається поруч із процесом (наприклад, `process/migration/review.md`).

## 4. Відповідність 1 : 1 та іменування

### 4.1. Іменування
- **Звіт експерименту:** `experiments/AV-xx/report.md`.
- **Рецензія експерименту:** `experiments/AV-xx/review.md`.
- **Рецензія специфікації:** зберігається у `specs/kpol/reviews/` із посиланням на конкретну версію специфікації (наприклад, `kpol-0.2-0.9-audit-review.md`).
- **Зведений аудит:** `process/audit/reports/Audit-<YYYY-MM-DD>-<тег>.md`.
- Ім'я рецензента у назву файлу не вноситься; агент та родина моделей обов'язково зазначаються у шапці документа.

### 4.2. Один документ — один Review Report
- На кожен Report або Specification ведеться **один** Review Report.
- Кілька рецензентів пишуть в одному Review Report окремими розділами: наприклад, «Рецензія версії 1.0 — рецензент Copilot (Claude Opus)», «Рецензія версії 1.0 — рецензент Gemini (Gemini)».
- Відповідь автора на знахідки й повторна рецензія — нові розділи в тому самому Review Report, а не нові файли.

### 4.3. Виняток: зведений аудит
Аудит, що охоплює кілька документів одночасно (наприклад, аудит за методикою ASPICE 4.0), оформлюється окремим звітом у `process/audit/reports/`. Реєстр перелічує всі охоплені документи, а кожен перевірений Report або Specification посилається на аудит у своїй шапці чи історії версій. Зведений аудит не скасовує наявності парних `review.md` для конкретних звітів, а доповнює їх.

## 5. Версіонування

1. **Версія — всередині документа за SemVer 2 (MAJOR.MINOR.PATCH).** Шапка містить поле `* **Версія:** X.Y.Z`, а наприкінці (перед розділом «Абревіатури та глосарій») є таблиця «Історія версій». Попередні редакції доступні в історії git.
2. **Версія Review Report вказує об'єкт перевірки.** Шапка рецензії чітко фіксує версію та commit SHA рецензованого документа за [шаблоном](../docs/templates/review.md): `* **Версія:** 0.1.0 (рецензує версію <X.Y.Z> звіту, коміт <SHA>)`.
3. **Правила зміни версії ([PROJECT-MANUAL §7](PROJECT-MANUAL.md#7-керування-конфігурацією)):**
   - **MAJOR:** зміна прийнятих тверджень, вимог, методу або висновків;
   - **MINOR:** нові розділи, звіти або твердження без зміни раніше прийнятих;
   - **PATCH:** редакційні правки, уточнення посилань чи глосарію без зміни змісту.
   Кожна зміна обов'язково супроводжується рядком в «Історії версій» із зазначенням номера Issue.

### 5.1. Обов'язкові поля шапки (за шаблонами)

| Report ([docs/templates/report.md](../docs/templates/report.md)) | Review Report ([docs/templates/review.md](../docs/templates/review.md)) |
| :--- | :--- |
| Версія (`X.Y.Z`) | Версія (рецензує версію `<X.Y.Z>` або PR, коміт `<SHA>`) |
| Дата (`YYYY-MM-DD`) | Дата (`YYYY-MM-DD`) |
| Issue (#N), PR (#M) | Звіт / Об'єкт (посилання), Issue (#N) |
| Виконавець (агент, модель або людина) | Рецензент (агент, модель або людина), сесія агента (ідентифікатор або шлях до логу; для людини — «—»), конфлікт інтересів |
| Рецензент (хто), посилання на Review Report | Вердикт (§6) |
| Коміт SHA, хост/плата, бітстрім SHA-256 (якщо є) | — |
| Критерії успіху (зафіксовані до виконання) | — |

## 6. Цикл рецензування й вердикти

```text
Чернетка → На рецензії → (Потрібні виправлення → нова версія → На рецензії)… → Вердикт
```

| Вердикт | Значення |
| :--- | :--- |
| **Прийнято** | Висновки випливають із даних; відтворено або перевірено за сирими даними |
| **Прийнято із зауваженнями** | Ядро результату коректне; виявлені недоліки не блокують мету й винесені в окремі Issues |
| **Доопрацювати** | Без виправлень приймати не можна; автор випускає нову версію звіту або коду |
| **Відхилено** | Головні висновки не випливають із даних або дані недостовірні |
| **Не перевірено** | Немає можливості перевірити; причина обов'язково зазначається |

Знахідки нумеруються в межах Review Report або прив'язуються до номерів Issues у трекері та мають рівні серйозності: **критична** (`sev:critical`), **значна** (`sev:major`), **незначна** (`sev:minor`).

Статус експерименту чи компонента в планах, вимогах, архітектурі та паспорті TRL оновлюється лише після отримання вердикту «Прийнято» або «Прийнято із зауваженнями».

## 7. Git

1. Автор комітить лише свої Report, сирі дані й скрипти. Рецензент комітить лише свій Review Report і власні контрольні сирі дані.
2. Рецензент не виправляє чужий документ чи код у PR автора; знахідки фіксуються виключно у Review Report та трекері Issues.
3. Коміти оформлюються за Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`, `exp:`) із зазначенням номера Issue (`#<N>`) у заголовку або тілі.
4. Префікси гілок прив'язані до номерів Issues: `<тип>/<N>-<коротко-латиницею>` (див. [PROJECT-MANUAL §3.1](PROJECT-MANUAL.md#3-робочий-процес-workflow)).

## 9. Звідки походять ці вимоги

Правило «один звіт — одна рецензія з тією самою версією» в такому вигляді — **конвенція цього проєкту**. Жоден стандарт не вимагає саме такої схеми іменування й папок. Але її складники запозичено з таких джерел:

| Джерело | Що звідти взято | Як перевірено |
| :--- | :--- | :--- |
| **Automotive SPICE 4.0** (VDA QMC, 2023), **SUP.1 Quality Assurance** | BP1: забезпечення якості виконується незалежно й об'єктивно, без конфлікту інтересів; приміткою прямо виключено самоконтроль («no self-monitoring»). BP3: оцінювати робочі продукти за визначеними критеріями й документувати результат. BP6–BP7: невідповідності відстежувати й ескалювати | Звірено з текстом PAM 4.0 |
| ASPICE 4.0, інформаційні елементи **13-19 Review evidence** і **13-25 Verification results** | Зміст Review Report: що перевірено, хто рецензенти, критерії, знахідки (невідповідності й пропозиції), статус. Результати перевірок: пройдено / не пройдено / не виконано з обґрунтуванням, дата, об'єкт | Звірено з текстом PAM 4.0 |
| ASPICE 4.0, **SUP.8 Configuration Management**, **SUP.9 Problem Resolution Management** | Версіонування й фіксація конкретного стану документа; відстеження знахідок до закриття | Назви процесів звірено; деталі — за загальним змістом |
| **Automotive SPICE 3.1** (2017): **SUP.2 Verification**, **SUP.4 Joint Review** | Окремі процеси верифікації та спільного перегляду робочих продуктів. У 4.0 цих процесів уже немає; перевірку описано в самих інженерних процесах (SYS.4–5, SWE.4–6, HWE.3–4) | Відсутність у 4.0 і назви процесів 4.0 звірено з PAM 4.0; зміст 3.1 — з пам'яті |
| **ISO 26262:2018** (функційна безпека автомобільних систем), частини 2 і 8 | Заходи підтвердження (confirmation review, audit, assessment) з рівнями незалежності I0–I3; верифікація з окремим звітом про верифікацію | З пам'яті; перед посиланням у зовнішніх документах звірити номери розділів |
| **IEEE 1028-2008** «Software Reviews and Audits» | Типи перевірок (технічна рецензія, інспекція, аудит), ролі (автор, рецензент, аудитор) і вихідний документ кожної перевірки | З пам'яті |
| **DO-178C**, **IEC 61508** | Вимога виконувати частину перевірок «з незалежністю» для критичних рівнів | З пам'яті |
| **ISO 9001:2015** (і військовий **AQAP-2110**, що на ньому базується) | Перегляди й верифікація проєктування (8.3.4), керування документованою інформацією та її версіями (7.5), внутрішній аудит (9.2) | З пам'яті |
| Наукова практика | Попередня реєстрація гіпотез і критеріїв, рецензування, сирі дані й походження | [План експериментів, §2](../experiments/PLAN.md) |

Отже, ASPICE — одне з джерел, а не єдине: з нього взято незалежність QA і зміст запису рецензії. Найсуворіші вимоги до незалежності — в ISO 26262, IEC 61508 і DO-178C. Ролі й типи рецензій найдокладніше описано в IEEE 1028.

Стандарти безпеки (ISO 26262, DO-178C, IEC 61508) тут — лише джерело практик рецензування. Проєкт їм не відповідає й не заявляє цього: див. [позицію щодо стандартів безпеки](standards-position.md). Подальші кроки за ASPICE 4.0 — у [плані кроків](aspice-steps.md).

### Глосарій

| Термін | Визначення |
| :--- | :--- |
| Аудит | Перевірка кількох документів або відповідності процесу встановленим правилам. Результат — Review Report |
| Вердикт | Підсумкова оцінка рецензента за шкалою §6 |
| Знахідка | Окреме зауваження рецензента з номером (З1, З2, …), доказом і рівнем серйозності |
| Зведений аудит | Один Review Report, що охоплює кілька документів (§4.3) |
| Конфлікт інтересів | Обставина, через яку рецензент може бути необ'єктивним: участь у створенні предмета перевірки, зацікавленість у результаті |
| Незалежність | Рецензент не є автором документа й не залежить від нього в оцінці. Для ШІ-агентів визначається родиною моделей (Claude vs Gemini) |
| Перехідні положення | Тимчасові винятки для документів, створених до цих правил |
| Попередня реєстрація | Фіксація гіпотези й критерію успіху до отримання даних |
| Робочий продукт (work product) | Термін ASPICE для будь-якого результату роботи: документа, коду, даних. У 4.0 — «інформаційний елемент» (information item) |
| Сирі дані | Дані вимірювань до обробки, з яких можна заново отримати всі числа звіту |
| Специфікація (Specification) | Документ виконавця з вимогами, архітектурою, описом мови чи методикою |
| Report (звіт) | Документ виконавця із записом виконаної роботи та її результатів ([docs/templates/report.md](../docs/templates/report.md)) |
| Review Report (звіт рецензії) | Документ рецензента, аудитора чи перевіряльника з результатом перевірки одного Report або Specification ([docs/templates/review.md](../docs/templates/review.md)) |
