# Постановка проблеми: Подолання вузького місця обробки підписок (Callback Bottleneck) у подієвих архітектурах

* **Версія:** 0.2.0
* **Дата:** 2026-11-13
* **Тип WP:** Problem
* **Власник:** Микола Федчик; автор гіпотези — Микола Федчик.

## Питання і призначення

У подієвій моделі Машини Кузьміна (МК) на ПЛІС час апаратної детекції події, фільтрації та зміни стану активної пам'яті BRAM становить фіксовані $80\text{ нс}$ із нульовим апаратним джитером ($\sigma_{\text{exec}} = 0\text{ нс}$). Проте, якщо подія генерує розгалуження (Fan-Out) на десятки споживачів (підписників, підпрограм або нано-колбеків), виникає системний бар'єр затримки:
1. **Накладні витрати послідовних шин (UART, SPI, CAN):** Зовнішні мікроконтролери (MCU) отримують сповіщення через шини з латентністю $10\dots 1000\ \mu\text{с}$.
2. **Розсип дискретних MCU:** Спроба виділити окремий фізичний MCU на кожну підписку створює схемотехнічну надмірність, збільшує енергоспоживання плати і ризик десинхронізації шин.
3. **Накладні витрати хост-драйвера GPU (`cudaLaunchKernel`):** Графічні процесори мають тисячі ядер і надшвидку пам'ять, проте класичний виклик ядра через драйвер ОС Linux має затримку $3\dots 10\ \mu\text{с}$, що неприйнятно для реального часу.

**Головне дослідницьке питання:**  
*Чи можливо організувати зв'язок між ПЛІС (МК) та GPU таким чином, щоб за один такт шини передавати зведений реєстр подій безпосередньо у швидку пам'ять GPU (SRAM / Shared Memory / L2 Cache), де постійно активний персистентний кернел розпаралелює виконання сотень нано-підписок на універсальних шейдерних ядрах (CUDA Cores / Stream Processors) без втручання хост-драйвера та із затримкою $T_{\text{e2e}} \le 1.0\ \mu\text{с}$?*

## Контекст і межі

1. **Відоме (Prior Art):**
   * ПЛІС забезпечує детермінований час рефлексу ($80\text{ нс}$).
   * Технології GPUDirect RDMA / PCIe Direct дозволяють записувати дані в BAR GPU без участі центрального процесора (CPU).
   * Персистентні кернели CUDA (Persistent Threads / Mega-Kernels) здатні працювати у нескінченному циклі опитування прапорців пам'яті без повторної ініціалізації драйвером.
2. **Припущення (включно з уточненням щодо типу обчислювачів):**
   * Підписники (нано-колбеки) є скалярними або векторними мікрофункціями (ПІД, поліноми, фільтри), стан яких компактно утримується в Shared Memory або регістрах SM.
   * Виконання підписок покладається виключно на універсальні шейдерні АЛП (CUDA Cores / Stream Processors / Xe Vector Engines) через їхню підтримку однотактових бітових інструкцій (`BFE`, `LOP3`) та предикатного виконання (`SEL`), тоді як тензорні блоки (Tensor Cores) відкидаються як невідповідні скалярній природі задачі.
   * Інтерфейс зв'язку між ПЛІС та платформою GPU забезпечує передачу бітової маски подій за час, що не перевищує $500\text{ нс}$.
3. **Суттєві невідомі:**
   * Реальна латентність реакції персистентного кернела GPU при переході від очікування до виконання на архітектурі NVIDIA Orin (Ampere architecture).
   * Вплив конкуренції за кеш L2 та ліній зв'язку шини між ПЛІС і пам'яттю GPU на джитер $\sigma$.

## Очікуваний результат і спростовні критерії

Гіпотеза вважається **підтвердженою**, якщо:
1. Повний наскрізний час від виникнення події на ПЛІС до фіксації результату виконання підписників у GPU задовольняє:
   $$T_{\text{e2e}} \lt 1.0\ \mu\text{с}$$
2. Апаратний джитер затримки на 1000 послідовних вимірюваннях не перевищує:
   $$\sigma_{\text{jitter}} \le 50\text{ нс}$$

Гіпотеза вважається **спростованою**, якщо:
1. Затримка опитування пам'яті GPU або внутрішні затримки диспетчеризації варпів перевищують $2.0\ \mu\text{с}$.
2. Енергетичні та теплові витрати постійно активного персистентного ядра роблять систему непридатною для вбудованих застосувань (виділення тепла понад допустимий бюджет модуля J501).

## Абревіатури та глосарій

* **BAR** (Base Address Register) — базовий адресний регістр простору PCIe/AXI.
* **Callback Bottleneck** — вузьке місце затримки виконання підписок на події.
* **Persistent Mega-Kernel** — ядро GPU, запущене один раз, що безперервно опитує буфер подій.
* **SM** (Streaming Multiprocessor) — потоковий мультипроцесор графічного чіпа.
