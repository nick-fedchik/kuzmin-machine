# Автоматична структурна перевірка трасування чисел у звітах

* **Версія:** 0.1.0
* **Дата:** 2026-11-10
* **Підстава:** [Issue #59](https://github.com/nick-fedchik/kuzmin-machine/issues/59), [PLAN §2](../experiments/PLAN.md#2-правила-обєктивності).

## Межі перевірки

`check_report_provenance.py` рекурсивно перевіряє всі `.md` і `.txt` у
`experiments/`, незалежно від регістру розширення, назви та ідентифікатора
експерименту. Рецензії також включені. Явні виключення: кореневий `PLAN.md`
(протокол, не звіт) та каталоги `raw/` і `scripts/` (дані й інструменти,
не місце зберігання підсумкових звітів). Історичні копії в `docs/research/`
та архіви не є новими експериментальними звітами. Порожній обсяг перевірки
дає `STRUCTURAL_FAIL`, а не порожній успіх.

Інструмент консервативно вважає числовим **кожен рядок із символом, для якого
Python `str.isnumeric()` істинне**, зокрема заголовки, ідентифікатори, версії,
таблиці й код. Виключень для «незручних» результатів немає. Числа, записані
словами, не розпізнаються. Це перевірка структурного трасування, а не
семантичний аналіз довільної природної мови.

`STRUCTURAL_PASS` означає лише повне покриття цих рядків метаданими за
форматом. Це **не** статус «походження підтверджено» і не проходження S1.
JSON завжди містить `s1_status: NOT_ASSESSED`, `result_values_verified: false`
і `metadata_authenticated: false`. Інструмент **не доводить**, що наведене
число правильно обчислено з вибірки, команда справді виконувалася чи
експеримент відтворюється. Відтворюваність —
[окрема Issue #75](https://github.com/nick-fedchik/kuzmin-machine/issues/75).
Команди з метаданих ніколи не виконуються перевіряльником.

## Контракт машинного трасування

Поруч із кожним `report.md` розміщується `report.provenance.json`
(для інших імен — та сама основа й суфікс `.provenance.json`).
Це технічне представлення вже встановленого критерію, не зміна гіпотези.

| Поле | Вимога |
| :--- | :--- |
| `report_sha256` | SHA-256 точних байтів звіту; редагування робить покриття застарілим |
| `runs` | Непорожній список записів про фактичні прогони |
| `runs[].command` | Фактична команда з параметрами, не припущений рецепт запуску |
| `runs[].git_commit` | Повний SHA коміту, доступного в локальному Git; не `unknown` |
| `runs[].timestamp` | ISO 8601 із часовим поясом; не раніше committer date коміту й не пізніше часу перевірки |
| `runs[].host` | Хост або плата, не заглушка |
| `runs[].raw` | Непорожній список об'єктів `path` / `sha256` |
| `runs[].raw[].path` | Шлях від кореня репозиторію до файла всередині `raw/` цього експерименту |
| `runs[].raw[].sha256` | SHA-256 точних байтів цього сирого файла |
| `runs[].lines` | Непорожній список номерів числових рядків звіту, починаючи з одиниці |

Кожен числовий рядок мусить належати хоча б одному валідному прогону.
Один запис може покривати кілька рядків, але це не перевіряє кожне значення
всередині рядка. Помилка будь-якого запису, непокритий рядок, відсутній файл
або невідповідність SHA дає `STRUCTURAL_FAIL` і код завершення `1`;
повне структурне покриття — `STRUCTURAL_PASS` і код `0`.
**Код `0` не можна використовувати як дозвіл проходження S1.**
Новий звіт автоматично входить до перевірки без списку дозволених файлів.

Навіть узгоджені дати не автентифікують запис. Назва хоста й рядок команди
є твердженнями автора метаданих; довільний whitelist хостів або хеш скрипта
не доводить факт виконання. Для такого висновку потрібні первинні журнали
виконання та незалежна перевірка. Перевіряльник не підміняє їх конфігурацією.

**Історичні дані не переписувати.** Відсутній sidecar означає, що автоматичне
трасування не підтверджене цим інструментом; сам по собі він не доводить
відсутність походження в старому довільному форматі. Старий SHA іншого
репозиторію не підміняти поточним SHA. Відсутні метадані не відновлювати
здогадками: потрібен доказ із первинного запису або окремий новий прогін.

## Запуск

```bash
python3 tools/check_report_provenance.py
python3 tools/check_report_provenance.py --json
python3 -m pytest tools/tests/test_report_provenance.py -q
```

Для перевірки окремого клону є `--root`. За замовчуванням корінь визначається
за розташуванням скрипта, не за поточним каталогом оболонки.
JSON-вивід містить SHA звітів, інвентар числових рядків, покриття й помилки.
Інструмент не є обов'язковим зеленим кроком CI для всіх історичних даних:
негативний аудит зберігається як результат, а не приховується заглушками.
CI виконує позитивні та негативні синтетичні тести самого перевіряльника.

## Абревіатури та глосарій

| Термін | Значення |
| :--- | :--- |
| AV | Ідентифікатор експерименту з плану на наявному обладнанні |
| CI | Автоматичні перевірки змін |
| SHA | Контрольна сума файла або ідентифікатор коміту Git |
| Sidecar | Сусідній JSON-файл, що зв'язує рядки звіту з доказами |
