## 1. Призначення та межі

KPOL досліджує спільне подання вимог (`Problem`) і реакцій на події (`Solution`), щоб простежити зв'язок від вимоги до її перевірки. Це не твердження, що наявні формальні методи не розв'язують цю задачу, і не доказ переваг Машини Кузьміна (МК).

v0.1 визначає лише типізовані стани, події, логічні умови та набір правил з атомарними записами. Вона не містить повної моделі мережі концептів МК, фазового оператора Великої крапки `•`, фізичних впливів `Pin`, циклів, довільних викликів, синтезу RTL або часової логіки. Поведінку інших конструкцій не визначено.

## 2. Типи, вимоги та час

### 2.1. Типи

| Тип | Домен і обмеження |
|---|---|
| `Bool` | логічні значення `true`/`false`; `Unknown` допустимий у вхідних даних події та проміжних обчисленнях, але не зберігається у стані |
| `Int32` | цілі \([-2^{31}, 2^{31}-1]\) |
| `U64` | цілі \([0, 2^{64}-1]\) |
| `Float<Unit>` | скінченне числове значення з одиницею; вхідні дані події можуть мати значення `Unknown` |
| `Pin` | зарезервований описовий тип; v0.1 не читає і не записує фізичні виводи |
| `Void` | відсутність результату; не є типом стану |

`Unknown` — відсутнє, невалідне або невідоме значення, а не нуль чи `false`. Арифметика з ним та звичайні порівняння повертають `Unknown`; спеціальні вирази `x == Unknown` і `x != Unknown` перевіряють наявність значення. Логіка з трьома значеннями: `false and Unknown = false`, `true and Unknown = Unknown`, `true or Unknown = true`, `false or Unknown = Unknown`, `not Unknown = Unknown`. Вхід приймається лише тоді, коли всі застосовні припущення дорівнюють `true`; інакше його відхиляють. `Unknown` не можна записати у звичайний стан.

Одиниці є частиною статичного типу: `Float<V> * Float<A> = Float<W>`, `Float<W> * Float<s> = Float<J>`. Додавання та порівняння потребують сумісних одиниць; v0.1 забороняє арифметику з абсолютною `Float<degC>` і не визначає явних перетворень (наприклад, J↔Wh або °C↔K). Безрозмірний числовий літерал може набути одиниці операнда лише під час порівняння або ініціалізації. `NaN` і нескінченність не допускаються. Використані позначення фізичних одиниць відповідають Міжнародній системі одиниць (SI) [1].

### 2.2. Значення вимог і порядок обробки подій

| Ключове слово KPOL | Значення у v0.1 |
|---|---|
| `Assumptions` | Передумови початкового стану або вхідних даних події (`on Event`). Перевіряються до звичайних правил; `false` чи `Unknown` відхиляє вхід. |
| `Invariants` | Логічні умови стану. Перевіряються на старті й після кожної транзакції; `false` чи `Unknown` відхиляє весь кандидат стану. |
| `Hazards` | Подієві логічні умови спостереження (`on Event to StateName`). Оцінюються на вхідних даних і знімку стану перед обробкою події, навіть якщо подію згодом відхилено; `Unknown` реєструється як `UnknownHazard`. Ціллю може бути лише логічний стан; фізичної реакції немає. |
| `Goals` | Логічні умови, які перевіряються після спорожнення черги подій. Це не властивість прогресу і не гарантія завершення. |

Зовнішні події обробляються за правилом «першим надійшов — першим оброблений» (FIFO). На старті перед зовнішніми подіями до черги додається по одній події `change` для кожного унікального набору підписки; нові внутрішні події додаються в кінець черги. Усі умови правил однієї події читають той самий знімок стану; записи збираються в буфер. Якщо умова має значення `Unknown`, обробку цієї події відхиляють і формують діагностику. Спроба записати різні значення в одну змінну в межах транзакції спричиняє відхилення. Після перевірки сталих умов новий стан або атомарно фіксується, або цілком відкидається. Зміна будь-якої змінної, за якою стежить `on change(A, B)`, додає відповідну подію до кінця черги FIFO.

Якщо `Assumption` не дорівнює `true`, звичайні правила події не запускаються, стан не змінюється, а журнал отримує запис `RejectedInput`. За наявності правила `on reject Event` виконується окрема логічна транзакція для реакції на відмову; без такого правила залишається явна діагностика, а старе значення не приймається мовчки. Помилка сталої умови також відхиляє транзакцію й реєструє діагностику. Межа транзакції охоплює лише логічний стан; зовнішніх побічних дій v0.1 не має.

`Goal` перевіряється лише тоді, коли черга подій порожня. Оператори `always`, `eventually`, `within` і часові граничні строки не входять до граматики; жодна властивість завершення не випливає лише з `Goal`.

У v0.1 `Assumption` може бути прив'язаний до події або початкового стану; `Invariant` і `Goal` — лише умови стану; кожен `Hazard` має бути прив'язаний до події.

## 3. Формальна граматика KPOL v0.1

Ця граматика є нормативною лише для вказаної підмножини. Неочікувані елементи, дублікати, невідомі імена, несумісні типи або хибно побудовані блоки мають спричиняти діагностику з місцем помилки, а не ігноруватися. Лексичний аналізатор також розпізнає коментарі `# ...`, `// ...` і `/* ... */`. Запис EBNF тут визначає саме наведені правила; відповідність окремому стандарту EBNF не заявляється [3].

```ebnf
module          = "Problem", Identifier, "{", problem-section*, "}",
                  "Solution", Identifier, "{", solution-item*, "}", EOF ;
problem-section = "Assumptions", "{", requirement*, "}"
                | "Invariants",  "{", requirement*, "}"
                | "Hazards",     "{", requirement*, "}"
                | "Goals",       "{", requirement*, "}" ;
requirement     = Identifier, [ "on", Identifier ], [ "to", Identifier ],
                  ":", expression, ";" ;
solution-item   = event-decl | state-decl | rule ;
event-decl      = "event", Identifier, "(", [ parameters ], ")", ";" ;
parameters      = parameter, { ",", parameter } ;
parameter       = Identifier, ":", type ;
state-decl      = "state", Identifier, ":", type, "=", expression, ";" ;
type            = "Bool" | "Int32" | "U64" | "Pin"
                | "Float", "<", Identifier, ">" ;
rule            = "rule", Identifier, "on", [ "reject" ],
                  event-spec, [ "when", expression ],
                  [ "covers", Identifier ], block ;
event-spec      = Identifier
                | "change", "(", Identifier, { ",", Identifier }, ")" ;
block           = "{", { "set", Identifier, ":=", expression, ";" }, "}" ;
expression      = boolean-or ;
boolean-or      = boolean-and, { "or", boolean-and } ;
boolean-and     = comparison, { "and", comparison } ;
comparison      = sum, [ ("==" | "!=" | "<" | "<=" | ">" | ">="), sum ] ;
sum             = product, { ("+" | "-"), product } ;
product         = unary, { ("*" | "/"), unary } ;
unary           = ("not" | "-"), unary | primary ;
primary         = Number | "true" | "false" | "Unknown" | Identifier
                | "gcd", "(", expression, ",", expression, ")"
                | "(", expression, ")" ;
Identifier      = Letter, { Letter | Digit | "_" } ;
Number          = Digit, { Digit }, [ ".", Digit, { Digit } ] ;
```

Пріоритет виразів задається граматикою EBNF; двомісні оператори групуються зліва направо. Великі й малі літери в ідентифікаторах розрізняються; зарезервовані слова не можна використовувати як імена. `gcd` — єдина вбудована функція. `change(...)` — єдина форма автоматично породжуваної події. Не передбачено гілки за замовчуванням, вихідного виводу, апаратного такту чи фізичного тлумачення часу.

## 4. Перетворення вимог на перевірки

| Ключове слово | Що робить еталонна реалізація | Перевірка та межа висновку |
|---|---|---|
| `Assumption` | Створює перевірку вхідних даних. Результат, відмінний від `true`, дає `RejectedInput` і запускає явне правило відхилення, якщо воно задане. | Випробування охоплюють коректні, хибні, `Unknown` і граничні вхідні дані. Це не підтверджує калібрування чи фізичну придатність давача. |
| `Invariant` | Створює перевірку стану після транзакції; невдала перевірка відхиляє запропоновані зміни. | Випробування під час виконання та перевірки властивостей охоплюють виконані переходи. Вичерпна перевірка обмежена скінченною тестовою множиною; загального доведення немає. |
| `Hazard` | Реєструє спостереження за знімком стану перед подією та її вхідними даними; `Unknown` дає окрему діагностику. `Hazard` явно називає цільовий логічний стан через `to`; правило `covers` має використовувати ту саму подію, тотожну умову й установлювати саме цю ціль у `true`. | Статична перевірка цілі, умови та дії, а також випробування позитивних і негативних випадків. Це не обґрунтування функційної безпеки й не гарантія фізичної реакції. |
| `Goal` | Формує результат перевірки після спорожнення черги подій. | Випробування повідомляють про виконання чи невиконання цілей. Завершення та граничні строки потребують окремого доведення або обмеженого аналізу. |

Розбірник і перевірка типів відхиляють невизначені імена, несумісні типи виразів, дублікати оголошень, невідомі події, неповне покриття небезпечних умов і арифметику з несумісними одиницями. Це виявляє структурні прогалини та помилки у перевірених сценаріях, але не доводить коректність довільної програми.

## 5. Коментарі й альтернативні записи символів

Лексичний аналізатор приймає коментарі `#`, `//` і `/* ... */`. Коментарі відкидаються під час лексичного аналізу; фігурні дужки всередині них не трактуються як синтаксис.

У v0.1 підтримуються і перевіряються лише такі альтернативні записи:

| Канонічний токен | Unicode-запис | ASCII-запис |
|---|---|---|
| Токен запису (зарезервований, не використовується в операторах v0.1) | `←` | `<-` |
| Токен читання (зарезервований, не використовується в операторах v0.1) | `→` | `->` |
| Токен фази (зарезервований, не виконується у v0.1) | `•` | `(*)` |

Обидва записи одного символу зводяться до того самого елемента лексичного аналізу й не додають поведінки під час виконання. `@dot`, `self`, `!`, `¬`, `_`, `::~` та інші попередні неоднозначні форми не є синтаксисом KPOL v0.1. Логічні значення записуються як `true` і `false`, відсутнє значення — як `Unknown`. Ці записи не є повним або взаємно-однозначним кодуванням усіх символів МК.

## 6. Приклади KPOL v0.1

Ці приклади можна виконати в еталонному інтерпретаторі. Їхні блоки коду безпосередньо завантажуються тестами з цього документа.

### 6.1. Монітор температури й тиску

Це лише логічна демонстрація умов, не контролер реактора і не реалізація IEC 61508 чи ISO 26262 [4, 5]. `Trip` не керує фізичним клапаном.

```kpol
Problem ReactorMonitor {
    Assumptions {
        TempValid on Sample: Temp != Unknown and Temp >= -50 and Temp <= 300;
        PressureValid on Sample: Pressure != Unknown and Pressure >= 0 and Pressure <= 50;
    }
    Invariants {
        FaultImpliesTrip: SensorFault == false or Trip == true;
    }
    Hazards {
        CriticalCombination on Sample to Trip: Temp > 120 and Pressure > 15;
    }
    Goals {
        NormalInputClearsFault: SensorFault == false;
    }
}
Solution ReactorMonitor {
    event Sample(Temp: Float<degC>, Pressure: Float<bar>);
    state SensorFault: Bool = false;
    state Trip: Bool = false;
    rule trip_on_critical on Sample when Temp > 120 and Pressure > 15 covers CriticalCombination {
        set Trip := true;
        set SensorFault := false;
    }
    rule clear_trip on Sample when Temp <= 120 or Pressure <= 15 {
        set Trip := false;
        set SensorFault := false;
    }
    rule reject_sample on reject Sample {
        set SensorFault := true;
        set Trip := true;
    }
}
```

### 6.2. Евклідове обчислення НСД

```kpol
Problem EuclidGCD {
    Assumptions {
        PositiveOperands: A > 0 and B > 0;
    }
    Invariants {
        DivisorPreserved: gcd(A, B) == gcd(OriginalA, OriginalB);
    }
    Goals {
        CompletedWithGCD: Done == true and A == B and Result == A;
    }
}
Solution EuclidGCD {
    state A: U64 = 48;
    state B: U64 = 18;
    state OriginalA: U64 = 48;
    state OriginalB: U64 = 18;
    state Result: U64 = 0;
    state Done: Bool = false;
    rule reduce_a on change(A, B) when A > B {
        set A := A - B;
    }
    rule reduce_b on change(A, B) when B > A {
        set B := B - A;
    }
    rule finish on change(A, B) when A == B {
        set Result := A;
        set Done := true;
    }
}
```

Еталонний інтерпретатор запускає початкову подію `change(A, B)` та додає нову після зміни A або B. Він обмежує кількість оброблених подій; досягнення межі завершується явною помилкою, а не вважається доведенням чи успішним результатом. Випробування перебирають скінченні додатні пари; це не загальний доказ завершення для всіх реалізацій чи типів.

### 6.3. Інтегрування енергії

`V` вимірюється у вольтах, `I` — в амперах, `dt` — у секундах, а `EnergyJ` — у джоулях. Для кожного прийнятого зразка використовується прямокутне чисельне інтегрування:

\[
E_J = \sum_{k=1}^{n} V_k \times I_k \times \Delta t_k
\]

```kpol
Problem EnergyMeter {
    Assumptions {
        ValidSample on Sample: V != Unknown and I != Unknown and dt > 0;
    }
    Invariants {
        NonNegativeEnergy: EnergyJ >= 0;
    }
    Goals {
        EnergyIsNonNegative: EnergyJ >= 0;
    }
}
Solution EnergyMeter {
    event Sample(V: Float<V>, I: Float<A>, dt: Float<s>);
    state EnergyJ: Float<J> = 0;
    state SensorFault: Bool = false;
    rule integrate on Sample {
        set EnergyJ := EnergyJ + V * I * dt;
        set SensorFault := false;
    }
    rule reject_sample on reject Sample {
        set SensorFault := true;
    }
}
```

Інтервал часу має бути вказаний для кожного зразка, а не задаватися прихованою сталою періодичністю. Похибка дискретизації, калібрування, втрата зразків і вимоги до точності окремо не моделюються.

## 7. Еталонна реалізація та випробування

`kpol_reference.py` містить лексичний аналізатор, що поділяє текст на елементи граматики, рекурсивний розбірник, абстрактне синтаксичне дерево (AST), перевірку типів і умов та детермінований еталонний інтерпретатор. Для розбору не використовуються регулярні вирази; числова арифметика `Float` спирається на тип `Decimal` зі стандартної бібліотеки Python [2]. `test_kpol_reference.py` запускається з каталогу `KuzminMachine`:

```sh
python -m unittest -v test_kpol_reference.py
```

Випробування розбирають усі три приклади з цього документа, перевіряють вкладені блоки, коментарі, альтернативні записи ASCII/Unicode, діагностику та несумісні одиниці. Перевірки властивостей перебирають скінченні набори вхідних даних для НСД, перевіряють інтегрування енергії й реакцію на `Unknown` та відхилені дані давача. Це регресійні перевірки підмножини v0.1, а не доказ коректності повної KPOL чи МК.

## 9. Порівняння парадигм і математична абстракція

### 9.1. Порівняння моделей

Наведені нижче підходи перетинаються, але не є взаємозамінними моделями виконання. ООП переважно описує структуру й організацію коду; автомати й Statecharts — стани та переходи; акторна модель — взаємодію незалежних обчислювачів; потоки даних — залежності між значеннями; формальна специфікація — спосіб точно задавати й аналізувати поведінку. **Інженерна рекомендація.** Для поточної підмножини доцільно визначати семантичне ядро як послідовну реакцію на одну подію: знімок стану перед її обробкою, буфер записів, розв'язання конфліктів, перевірку інваріантів і фіксацію або відхилення змін. Це рекомендація щодо ясності та перевірності, а не абсолютний рейтинг парадигм. ООП може бути додатковим структурним засобом, а перетворення потоків даних — окремим шаром, якщо їхні межі з транзакціями визначені. Конкурентність акторів або синхронні такти варто вводити лише за відповідної вимоги й окремої специфікації їхньої взаємодії з ядром.

### 9.2. Система переходів: математична абстракція

Описані в розділі 2 правила можна подати як систему переходів. Нижче наведено пояснювальну, пропоновану абстракцію для міркування про підмножину, а не нормативне формальне означення KPOL, доказ властивостей реалізації чи семантику будь-якої з порівнюваних мов.

Нехай \(S\) — множина типізованих відображень змінних стану у значення; \(P_n\) — домен допустимих даних (payload) події типу \(n\), тож \(E\) — множина типізованих подій, наприклад \(E=\bigcup_n\{n\}\times P_n\); \(Q\in E^*\) — скінченна FIFO-черга, де \(e\cdot Q\) означає перший елемент і решту черги. Нехай \(D\) — послідовність діагностик, тоді конфігурацію для аналізу можна записати як \(C=(s,Q,D)\), де \(s\in S\). Окреме надходження зовнішньої події додає її в кінець черги; воно не є обробкою цієї події.

Під час обробки першої події \(e\) умови `Assumption` і спостереження `Hazard` оцінюються на даних події та знімку стану до події \(s\); `Hazard` спостерігається навіть тоді, коли вхід згодом відхиляється. Звичайні умови правил оцінюються лише після того, як усі застосовні `Assumptions` мають значення `true`, і всі вони використовують той самий знімок \(s\). Якщо будь-яка `Assumption` має значення `false` або `Unknown`, звичайна обробка події відхиляється й реєструється `RejectedInput`; звичайні записи не застосовуються. Якщо умова звичайного правила має значення `Unknown`, транзакція події відхиляється з діагностикою. За відсутності такого відхилення запропоновані правилами записи збираються в часткове відображення \(W\) зі змінних у значення, а не застосовуються по черзі до проміжних станів. Якщо активні правила вимагають різних значень для тієї самої змінної, виникає конфлікт і транзакція відхиляється. Якщо записи узгоджені, з них формується кандидатний стан \(s'\); його фіксують лише тоді, коли всі інваріанти для нього істинні. Інакше зміни цієї транзакції відкочуються, стан лишається \(s\), а конфігурація отримує діагностику.

Успішний перехід можна схематично записати так:

\[
(s,e\cdot Q,D)\xrightarrow{e}(s',Q\cdot R,D'),
\]

де \(\xrightarrow{e}\) позначає успішну звичайну транзакцію для події \(e\), узгоджені записи визначають \(s'\), \(R\) — породжені нею події зміни, додані в кінець FIFO, а \(D'\) — діагностики після кроку. Ця схема не описує відхилену звичайну транзакцію: при відхиленні стан після неї лишається \(s\), а діагностика фіксує причину. Зокрема, коли `Assumption` має значення `false` або `Unknown`, `RejectedInput` записується, а наявне `on reject Event` виконується як окрема логічна транзакція; її можливі зміни стану не включені до наведеного переходу й мають бути подані окремим кроком. `Hazards` водночас оцінюються на початковому знімку \(s\) та даних події, незалежно від відхилення. Породжені події обробляють у наступних кроках, а не як миттєву реакцію всередині цього переходу. Коли \(Q=\varepsilon\), конфігурація перебуває у стані спокою (порожня черга), і тоді перевіряються `Goals`. Спорожнення черги не гарантується: нескінченне породження подій може перешкодити досягненню стану спокою.

Цей запис схематичний: він не додає правил справедливості, часових властивостей чи повного вибору між кількома правилами, а FIFO саме по собі не доводить детермінованість усіх виконань. Для формального доведення потрібні повні правила переходів і визначене скінченне або інше придатне до аналізу представлення стану та черги.

### 9.3. Межі KPOL v0.1

У межах цього документа KPOL v0.1 визначає **одну послідовно оброблювану глобальну FIFO-чергу**, типізовані стани й події, умови правил, буферизовані записи, відхилення конфліктних записів, атомарну логічну фіксацію після перевірки інваріантів або відкат, явне відхилення невідповідних даних і породження `change`-подій. Логічні цілі перевіряються після спорожнення черги; транзакції не мають зовнішніх побічних дій.

Підмножина **не визначає** синхронного годинника, логічних кроків (тактів) чи миттєвої реакції; темпоральних операторів на кшталт `always`, `eventually`, `within` або дедлайнів; незалежних акторів чи конкурентних обробників; ієрархії станів або ортогональних регіонів Statecharts; класово-об'єктного середовища виконання чи успадкування; а також фізичного часу або часових характеристик апаратури. Це межі саме заявленої підмножини, а не загальний висновок про можливі майбутні розширення.

Наведені мови й наукові праці є джерелами для порівняння понять і історичного контексту; їх цитування **не є свідченням відповідності KPOL** Esterel, Lustre, Signal, Statecharts або будь-якій іншій мові чи стандарту.

Якщо пропозиції для майбутньої версії розростуться, їх краще винести в окремий проєктний додаток до KPOL, а не подавати як уже чинні конструкції v0.1.

## 11. Глосарій

| Термін | Значення в цьому документі |
|---|---|
| Абстрактне синтаксичне дерево (`AST`) | Структуроване подання програми, створене розбірником; зберігає вкладеність і зв'язки між її частинами. |
| Альтернативний запис (`alias`) | Інше написання символу, яке зводиться до того самого елемента лексичного аналізу; не додає окремої поведінки. |
| Вхідні дані події (`payload`) | Значення параметрів, передані разом із конкретною подією. |
| Еталонний інтерпретатор | Виконувана реалізація, що задає поведінку підтриманої підмножини KPOL v0.1; це не компілятор і не модель апаратної реалізації. |
| Знімок стану (`snapshot`) | Набір значень стану, який правила читають під час обробки однієї події; записи цієї події ще не застосовано. |
| Умова правила (`guard`) | Логічний вираз, істинність якого визначає, чи виконується правило. |
| Небезпечна умова (`hazard`) | Умова, яку слід спостерігати як можливу небезпеку; її опис у KPOL v0.1 сам по собі не запускає фізичної реакції. |
| Стан спокою (`quiescence`) | Момент, коли черга подій спорожніла й більше немає подій зміни для обробки. Саме тоді перевіряються `Goals`. |
| Транзакція | Обмежена група логічних записів і перевірок для однієї події; усі записи фіксуються разом або відкидаються. |
| `Unknown` | Позначення відсутнього, невалідного чи невідомого значення; воно відрізняється від `false` та нуля. |
| Мережа концептів МК | Поняття з моделі Машини Кузьміна; KPOL v0.1 не задає її повної структури й подає лише обмежені логічні стани. |
