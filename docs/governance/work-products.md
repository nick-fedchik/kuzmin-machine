# Конфігурація Work Products

* **Версія:** 0.1.0 (проєктна угода)
* **Дата:** 2026-11-12
* **Призначення:** класифікація результатів НДДКР і навігація за їхнім призначенням.

Work Product (WP) — результат або збережений матеріал із конкретним
призначенням у проєкті. Первинні джерела каталогізуються як входи
дослідження, навіть коли не є результатом проєкту.

Для самостійної одиниці обирають один **основний тип за призначенням**,
не за назвою чи розширенням файлу. Окремо за потреби зазначають підтип,
область, походження, стан, формат і зв'язки з іншими матеріалами.
Розділ, запис у реєстрі або пакет файлів може бути WP; окремий файл для
кожної вимоги чи висновку не обов'язковий.

«Документація» — загальна назва для документів, не окремий основний тип.
`Analysis` і `Review` можуть бути призначенням `Report`; `ADR` — підтип
`Decision`. `Evidence` — роль матеріалу щодо конкретного твердження, а не
гарантія доказовості. Архівність — стан, а не тип. GitHub Issue відстежує
роботу й не обов'язково є окремим WP; види роботи описано в
[каталозі Work Items](../../process/work-items.md). Конкретні результати
для керування конфігурацією наведено в [реєстрі CI](../../process/configuration-items.md).

## 1. Словник WP

| Група | Тип | Призначення та ознака |
|---|---|---|
| Дослідження | `Source` | Первинний або сторонній матеріал, з якого беруть твердження чи дані |
| Дослідження | `Problem` | Питання, гіпотеза, контекст і межі дослідження |
| Дослідження | `Model` | Абстракція об'єкта для опису, міркування або обчислення |
| Дослідження | `Protocol` | Умови, порядок і критерії конкретної перевірки |
| Дослідження | `Report` | Результати й обмеження роботи; підтипи `Analysis`, `Experiment`, `Review`, `Assessment` |
| Дослідження | `Data` | Вимірювання, спостереження, траси або журнали з походженням |
| Інженерія | `Requirement` | Окрема перевірна потреба чи обмеження |
| Інженерія | `Specification` | Систематизовані правила, вимоги або контракт об'єкта |
| Інженерія | `Design` | Конструкція й взаємодія частин рішення, включно з апаратним проєктом |
| Інженерія | `Decision` | Вибір, його контекст і наслідки; архітектурний підтип — `ADR` |
| Інженерія | `Solution` | Сукупність частин, що розв'язує конкретну задачу |
| Інженерія | `Source Code` | Машиночитане визначення програми, інструмента чи тесту, зокрема RTL/HDL |
| Інженерія | `Configuration` | Параметри збирання, розміщення або виконання |
| Інженерія | `Hardware` | Фізичний пристрій чи прототип; у Git може бути лише його опис |
| Організація | `Plan` | Намічені мета, межі й кроки або етапи |
| Організація | `Guide` | Огляд, навігація чи інструкція для читача або виконавця |
| Організація | `Policy` | Правило, повноваження чи позиція проєкту |
| Організація | `Register` | Перелік сутностей із їхніми станами, зв'язками чи походженням |
| Організація | `Template` | Основа для створення іншого WP, а не сам результат |

Групи допомагають орієнтуватися, а не встановлюють жорсткі межі: модель
може бути інженерною, а звіт — про випробування апаратури. Шаблони —
[у каталозі шаблонів](../../process/templates/work-products/README.md).
Їх використовують за потреби, не створюючи документи лише заради процесу.

## 2. Правила розрізнення

1. `Source` зберігає походження; похідний аналіз — окремий `Report`.
   Не приписуй похідні висновки автору концепції.
2. `Requirement` — окрема вимога; `Specification` може об'єднувати
   вимоги та правила. Назва «специфікація» не підтверджує її затвердження.
3. `Design` описує конструкцію; `Decision / ADR` — вибір та його
   обґрунтування; `Solution` може включати обидва та реалізацію.
4. `Protocol` визначає перевірку, `Data` містить її результати,
   `Report` — висновки й обмеження; тестовий код є `Source Code`.
   Симуляцію, mock і випробування на фізичному обладнанні розрізняють.
5. `Report / Review` рецензує інший результат і не означає його прийняття.
   Негативний чи невизначений дослідницький висновок може бути результатом.
6. `README.md` — назва файлу, а не тип. Навігаційний README — `Guide`;
   самостійний аналіз зберігають окремо й посилаються на нього з README.
7. Розміщення, формат чи наявність звіту не доводять правильності,
   актуальності, прийняття, відповідності стандартам або завершення роботи.

## 4. Спільні ознаки та перегляд

За потреби для WP фіксують шлях чи локатор, основний тип, призначення,
походження, стан і зв'язки. Для дослідів та доказів суттєві версія або
дата, метод, умови, сирі дані, обмеження й стан рецензії, якщо вони є.
Не нав'язуй однакову шапку кожному історичному файлу чи сирому логу.

Під час перегляду обирають: залишити, об'єднати, архівувати, запропонувати
вилучення або відкласти рішення за браку даних. Перед вилученням чи
переміщенням перевіряють авторство, джерела, посилання, залежності,
архів і відтворюваність; рішення власника передує видаленню.
