## 1. Суть

Машина Кузьміна (МК) — дослідний прототип: RTL-вентиль `kpol_txn_gate`, еталонний компілятор KPOL, вимірювання на PYNQ-Z1. Згадки в репозиторії про **ISO 26262 / ASIL**, **DO-178C / DO-254 / DAL**, **IEC 61508 / SIL**, **IEC 62304 Class C** та **ISO/SAE 21434** означають лише:

- **цільові домени**, у яких МК, можливо, буде корисною;
- **припущення**, що архітектура з часом зможе дотягнутися до вимог цих стандартів.

Жодне з цього не підтверджено. Для МК **не виконано**:

- аналіз небезпек і ризиків (HARA за ISO 26262, оцінювання безпеки системи для авіації, аналіз ризиків за ISO 14971);
- визначення цілей безпеки та призначення ASIL / DAL / SIL;
- концепцію функціональної безпеки, план безпеки, обґрунтування безпеки (safety case);
- аналіз загроз і ризиків (TARA за ISO/SAE 21434);
- кількісні метрики апаратних відмов (для ISO 26262 — SPFM, LFM, PMHF);
- кваліфікацію інструментів (ISO 26262-8, DO-330);
- незалежне оцінювання або сертифікацію.

## 2. Правила формулювань

| Не писати | Писати |
| :--- | :--- |
| «МК забезпечує ASIL D / SIL 3 / DAL A» | «цільовий рівень ASIL D (гіпотеза, не підтверджено)» |
| «відповідає ISO 26262 / DO-178C», «повна відповідність» | «спроєктовано з урахуванням вимог …; відповідність не оцінювалася» |
| «ASIL D Safety Cage», «бар'єр ASIL D» | «апаратний бар'єр безпеки (цільовий рівень ASIL D — гіпотеза)» |
| «для проходження аудиту ISO 26262 компілятор формує …» | «як допоміжний артефакт для можливого майбутнього аудиту …» |
| «сертифіковано», «сертифікований модуль МК» | «до сертифікації», «за умови майбутньої сертифікації» |
| «скорочує обсяг сертифікаційних робіт на N %» | «за гіпотезою може скоротити … (оцінка не перевірена)» |
| «стандарт X вимагає Y» без джерела | точне формулювання з посиланням на пункт стандарту — або «за загальноприйнятою практикою …» |

Нейтральні згадки дозволені без застережень: опис стандарту як галузевого контексту, питання, критерії фальсифікації, вимоги до майбутніх рівнів TRL, роль аудитора.

## 3. Що знадобиться, перш ніж робити будь-яке твердження про відповідність

Перелік мінімальний, складений з пам'яті, з текстами стандартів **не звірявся** (вони платні). Перед застосуванням — звірити.

| Стандарт | Мінімальні передумови |
| :--- | :--- |
| ISO 26262 (авто, функціональна безпека) | Визначення об'єкта (item) — або, для компонента без конкретного автомобіля, SEooC із задокументованими припущеннями щодо використання; HARA → цілі безпеки → ASIL; план безпеки; підтвердні заходи з незалежністю; для апаратури — метрики відмов; довіра до інструментів (TCL) |
| ISO/SAE 21434 (авто, кібербезпека) | Визначення об'єкта або компонента поза контекстом; TARA → цілі кібербезпеки; захист інтерфейсів (AXI-Lite), цілісність і походження бітстріму, ланцюг постачання інструментів |
| DO-178C / DO-254 (авіація) | Рівень DAL призначає оцінювання безпеки системи (ARP4754A / ARP4761), а не розробник компонента; плани (PSAC / PHAC) погоджуються з органом сертифікації; кваліфікація інструментів — DO-330 |
| IEC 61508 (промисловість) | Аналіз небезпек → вимоги до функцій безпеки → SIL; кількісна оцінка відмов; оцінювання функціональної безпеки |
| IEC 62304 (медицина) | Клас безпеки ПЗ визначається з процесу керування ризиками за ISO 14971; IEC 62304 регулює процеси життєвого циклу ПЗ, а не конкретні апаратні рішення |

## 4. Що вже є і може знадобитися пізніше

Ці результати **не є** доказами відповідності, але можуть увійти в майбутню доказову базу:

- механізм fail-closed у `kpol_txn_gate` — кандидат у механізм безпеки; потребує моделі відмов і доказу діагностичного покриття;
- формальна перевірка AV-04 (BMC, k-індукція) — приклад формального методу верифікації;
- ідея трасування вимог у KPOL (RTM) — інструмент, а не відповідність;
- [правила документів і рецензування](review-rules.md) — зачаток незалежної перевірки (виконавці й рецензенти — ШІ-агенти, а не незалежні організації).

## 5. Коли переглянути цю позицію

- з'явився замовник або грантодавець із конкретною вимогою до стандарту;
- обрано конкретне застосування (домен, клас пристрою, роль МК у системі);
- проєкт готується до TRL 6 і вище.

До того часу ISO 26262, ISO/SAE 21434, DO-178C / DO-254, IEC 61508 та IEC 62304 у проєкт не впроваджуються. Процесна база — [ASPICE 4.0, прості кроки](https://github.com/nick-fedchik/kuzmin-machine/blob/707fdba697d92ef9874c9013eb6f4f3cb2796d70/process/aspice-steps.md).

## Абревіатури та глосарій

| Скорочення / термін | Значення |
| :--- | :--- |
| ASIL | Automotive Safety Integrity Level — рівень повноти безпеки в ISO 26262 (A…D, D — найвищий) |
| DAL | Design Assurance Level — рівень забезпечення розробки в DO-178C / DO-254 (A…E, A — найвищий) |
| SIL | Safety Integrity Level — рівень повноти безпеки в IEC 61508 (1…4) |
| HARA | Hazard Analysis and Risk Assessment — аналіз небезпек і оцінювання ризиків (ISO 26262) |
| TARA | Threat Analysis and Risk Assessment — аналіз загроз і ризиків (ISO/SAE 21434) |
| SEooC | Safety Element out of Context — елемент, розроблений без конкретного автомобіля, на основі припущень щодо використання |
| SPFM / LFM / PMHF | Метрики апаратних відмов ISO 26262: покриття одиничних відмов, латентних відмов, імовірнісна метрика випадкових апаратних відмов |
| TCL | Tool Confidence Level — рівень довіри до інструмента (ISO 26262-8) |
| DO-330 | Стандарт кваліфікації програмних інструментів в авіації |
| PSAC / PHAC | Plan for Software / Hardware Aspects of Certification — плани сертифікаційних аспектів ПЗ / апаратури |
| ARP4754A / ARP4761 | Авіаційні настанови з розробки систем і оцінювання їхньої безпеки |
| ISO 14971 | Стандарт керування ризиками медичних виробів |
| RTM | Requirements Traceability Matrix — матриця трасування вимог |
| BMC | Bounded Model Checking — обмежена перевірка моделі |
| fail-closed | Поведінка, за якої в разі сумніву або збою дія блокується |
| Safety case | Обґрунтування безпеки — структурований аргумент із доказами, що система прийнятно безпечна |
| TRL | Technology Readiness Level — рівень готовності технології |
