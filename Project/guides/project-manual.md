## 1. Мета й межі

**Мета:** розробити й перевірити апаратно-програмні компоненти Машини Кузьміна (МК): RTL-ядро на FPGA, мову KPOL та її еталонну реалізацію, засоби верифікації. Кожне твердження має спиратися на відтворювані докази.

**Входить у проєкт:** усі робочі дослідження, формальний аналіз і наукова опозиція; вимоги, архітектура, код HW/SW та інструменти; верифікація, експерименти AV-xx/EXP-xx, звіти, рецензії й оцінювання TRL; внутрішні плани й технічна аналітика. Перенесення документа не означає підтвердження його висновків.

**Окремий редакційний майданчик:** у `drafts/KuzminMachine` історично розміщувалися редакційні статті на перевірених фактах для вичитування Михайлом Кузьміним та передпублікаційного опрацювання (нині статті перенесено до `Articles/`). Актуальне [правило розміщення](../policies/layout.md) поглинає рішення власника 2026-11-10, Issue #84. Відповідність стандартам безпеки не заявляється (див. [standards-position.md](../policies/standards-position.md)).

**Поточний стан:** TRL 3 (PoC) за самооцінкою, див. [паспорт TRL](../assessments/trl/report.md). Незалежним аудитом не підтверджено.

**Мета MVP (TRL 4)** — прийнято власником 2026-11-09: рефакторинг у три кроки та усунення п'яти прогалин PoC ([план](../../Engineering/design/refactoring-plan.md)):

### 2.1. Агенти проєкту

| Агент | Файл інструкцій, який читає | Модель |
| :--- | :--- | :--- |
| GitHub Copilot CLI (Lead Engineer) | `AGENTS.md` | змінна (обирає користувач; зараз Claude Opus) |
| Claude Code | `CLAUDE.md` → `AGENTS.md` | Claude |
| Gemini CLI | `GEMINI.md` → `AGENTS.md` | Gemini |

**Незалежність визначає модель, а не інструмент.** Copilot з моделлю Claude і Claude Code — одна родина моделей. Тож рецензент має бути з **іншої родини моделей**, ніж автор: на роботу Claude — Gemini, на роботу Gemini — Claude. OpenCode та Copilot підходять, якщо в них обрано модель іншої родини. Тому в шапці кожного Report і Review Report вказують і агента, і модель. Аудитор за [методикою](https://github.com/nick-fedchik/kuzmin-machine/blob/707fdba697d92ef9874c9013eb6f4f3cb2796d70/process/audit/ASPICE-Audit-Method.md) — теж модель іншої родини, ніж автори об'єкта аудиту, і в чистій сесії.

### 2.2. Ліміт незавершеної роботи (WIP)

Рішення власника 2026-11-09 ([#46](https://github.com/nick-fedchik/kuzmin-machine/issues/46)). Одиниця роботи — **PR**, а не задача.

1. **Один відкритий PR на виконавця.** Нову задачу Lead Engineer видає агенту лише після того, як його попередній PR злито або закрито.
2. **Перехресна перевірка — етап того самого PR.** Рецензію моделлю іншої родини, виправлення автора за знахідками й повторну перевірку планують у межах одного PR. На кожен з цих етапів окрема задача чи PR не створюються: Review Report і повторна перевірка — коментарями в PR (або файлом `review.md` у тому ж PR, п. 3.1).
3. **Знахідка поза межами PR** оформлюється Issue (`type:finding`). Якщо вона блокує поточний PR, її виправляють у ньому ж (`Closes` кількох Issues) за рішенням Lead Engineer або власника. Якщо не блокує — вона чекає в беклозі.
4. Lead Engineer веде облік відкритих PR і етапу кожного з них (виконання → рецензія → виправлення → злиття) і видає задачі лише в межах п. 1. Облік перевірюваний: кожен етап лишає слід у самому PR (Report — у тілі, Review Report і повторна перевірка — коментарями, виправлення — комітами), а Status пов'язаної Issue в GitHub Project (§6) відповідає етапу.

## 3. Робочий процес (workflow)

```mermaid
flowchart LR
    B[Backlog] -->|власник: критерії приймання| R[Ready]
    R -->|виконавець бере| P["In progress<br/>гілка + worktree"]
    P -->|PR + Report| V[In review]
    V -->|Review Report| D{"Вердикт рецензента<br/>(вето власника)"}
    D -->|"Прийнято;<br/>Прийнято із зауваженнями<br/>(зауваження → нові Issues)"| M["Done<br/>merge не-автором"]
    D -->|Доопрацювати| P
    D -->|"Не перевірено<br/>(причина)"| V
    D -->|Відхилено| X["Closed: rejected"]
```

Правила:

1. **Одна Issue — одна гілка — один PR.** Схема гілок прив'язана до Issue:

   ```mermaid
   gitGraph
       commit id: "main"
       branch feat/14-gate-core
       commit id: "feat: #14 ..."
       commit id: "test: #14 ..."
       checkout main
       branch exp/12-av07-rerun
       commit id: "exp: #12 ..."
       checkout main
       merge feat/14-gate-core id: "PR Closes #14"
       merge exp/12-av07-rerun id: "PR Closes #12"
   ```

   - **Ім'я гілки:** `<тип>/<номер-issue>-<коротко-латиницею>`, наприклад `exp/12-av07-mutation-rework`.
     Типи: `feat` (код), `fix` (виправлення), `exp` (експеримент AV-xx), `spec` (специфікація чи вимоги), `docs`, `review` (Review Report), `audit` (звіт аудиту), `chore` (структура, CI).
     Гілку без номера Issue не створюють.
   - **Створення гілки:** `gh issue develop <N> --name <тип>/<N>-<опис> --base main` (зв'язує гілку з Issue) або `git worktree add … -b <тип>/<N>-<опис> origin/main`.
   - **Коміти** містять `#<N>` у заголовку або тілі.
   - **PR:** заголовок `<тип>: <опис> (#<N>)`, у тілі `Closes #<N>`. Review Report — коментар у PR або коміт рецензента в той самий PR, лише у файлі `review.md` (§2.2). Окремий PR з гілки `review/<N>-…` — лише для рецензії вже злитого документа.
   - **Злиття** — squash merge. Гілку видаляють після злиття. Довгоживучих гілок, окрім `main`, немає.
2. **Готовність до виконання (Definition of Ready):** Issue має мету, межі, критерії приймання (кількісні або булеві), посилання на вимоги `REQ-*` або гіпотези `H*`, а також мітку власника `ready`.
3. **Виконано (Definition of Done):**
   - CI зелений;
   - Report має шапку, версію, джерела даних і обмеження;
   - є Review Report з вердиктом «Прийнято» або «Прийнято із зауваженнями»; у другому випадку всі зауваження оформлено окремими Issues;
   - усі суттєві знахідки закриті або винесені в окремі Issues;
   - трасування оновлено;
   - PR злив учасник, який не є його автором.
4. **У `main` — лише через PR. Зливає будь-хто, крім автора PR**, за таких умов:
   - CI зелений;
   - є Review Report з вердиктом «Прийнято» або «Прийнято із зауваженнями» від рецензента, який не є автором; у другому випадку всі зауваження оформлено окремими Issues;
   - на PR є approve на GitHub від не-автора;
   - власник не наклав вето (мітка `blocked` або коментар).

   Агент зливає лише за явною командою людини. Теги ставить Lead Engineer за §7.1.
   Якщо план GitHub дозволяє, правило закріплюють захистом гілки: обов'язковий PR, 1 approve, заборона approve від останнього автора push, обов'язковий CI. Інакше правило діє через цей документ.

   **Конфігурація з одним обліковим записом GitHub** (діє, поки в репозиторії лише @nick-fedchik). Усі агенти працюють під цим обліковим записом, тож формально автор кожного PR — власник, і GitHub не дає йому approve. Тому:
   - **автор PR** — це виконавець (агент і модель), зазначений у Report або в тілі PR, а не обліковий запис GitHub;
   - умову «approve на GitHub від не-автора» замінює **Review Report із вердиктом «Прийнято» або «Прийнято із зауваженнями»** від рецензента іншої родини моделей (§2.1); у другому випадку всі зауваження оформлено окремими Issues. Review Report — файл `review.md` у PR або коментар у PR, в обох випадках з усіма полями й розділами [шаблону](../templates/review.md);
   - Review Report пише **окрема сесія** агента-рецензента; у шапці — агент, модель та ідентифікатор сесії або шлях до її логу. Lead Engineer не публікує Review Report від імені іншого агента. Власник вибірково звіряє заявлене з логами сесій;
   - **зливає власник** (squash merge) після перевірки решти умов цього пункту.

   Правило втрачає силу, щойно з'являється другий обліковий запис з правом запису: тоді діє approve на GitHub.
5. **Зовнішні й незворотні дії** виконуються лише за явною командою власника: створення чи видалення репозиторіїв, force-push, зміна видимості, публікація, витрати.
6. **Єдиний виняток з п. 4:** стартовий коміт порожнього репозиторію (`README.md`, `.gitignore`) іде прямо в `main`, бо PR без базової гілки неможливий. Зроблено один раз, 2026-11-09.

## 5. Орієнтир процесів ASPICE

ASPICE використовується добровільно як орієнтир добрих практик; зовнішньої
вимоги немає. Для поточного планування використовуємо PAM 4.1. Орієнтовна
мета — рівень можливостей 1 для процесів нижче; рівень 2 для обраних
процесів є бажаною перспективою, а не підтвердженим станом чи обов'язковою
умовою всього проєкту. Самооцінка не замінює формального оцінювання.
Раніші методики й звіти, що посилаються на PAM 4.0, зберігають свою
версію та не стають автоматично оцінкою за 4.1.

Доступ до локальної копії PAM 4.1 і обмеження поширення визначають
[позиція щодо стандартів](../policies/standards-position.md) та рішення власника.

## 7. Керування конфігурацією

- **Елементи конфігурації:** Git версіонує відстежувані файли; конкретні
  кандидати для керування конфігурацією — у [реєстрі CI](../registers/configuration-items.md).
  Великі сирі дані можна винести в Releases з контрольною сумою — це рішення власника.
- **Версії документів — Semantic Versioning 2.0.0:** `MAJOR.MINOR.PATCH` у шапці (`* **Версія:** X.Y.Z`).
  - `0.y.z` — чернетка; `1.0.0` — перша прийнята редакція (є Review Report «Прийнято»).
  - PATCH — редакційні правки без зміни змісту; MINOR — нові розділи або твердження без зміни прийнятих; MAJOR — зміна прийнятих тверджень, вимог чи висновків.
  - Кожна зміна — рядок в «Історії версій». Review Report вказує версію, яку рецензує.
  - У межах одного незлитого PR версію документа підвищують **один раз**: виправлення за рецензією доповнюють рядок історії цієї версії, а не створюють нову. Рецензія посилається на коміт.
  - Файли специфікацій мають версію в імені (`kpol-0.9.0.md`); інші документи — ні.
- **Версія репозиторію:** файл [`VERSION`](https://github.com/nick-fedchik/kuzmin-machine/blob/707fdba697d92ef9874c9013eb6f4f3cb2796d70/VERSION) і анотований тег `vX.Y.Z`, який ставить Lead Engineer за §7.1. `v0.4.0` — міграція PoC (апаратний PoC мав `0.3.0`); `v1.0.0` — MVP / TRL 4. Перед аудитом ставиться тег, і аудит посилається на нього.
- **Сирі дані незмінні:** повторний прогін записується в новий каталог (у скриптах AV — змінні середовища `AV0x_OUT_DIR`).
- **Походження перенесеного:** рядок `* **Перенесено з:**` у шапці та [скрипт міграції](https://github.com/nick-fedchik/kuzmin-machine/blob/707fdba697d92ef9874c9013eb6f4f3cb2796d70/process/migration/migrate_from_drafts.py).

### 7.1. Тегування

Тегування делеговано Lead Engineer рішенням власника 2026-11-09 ([#29](https://github.com/nick-fedchik/kuzmin-machine/issues/29)).

1. Анотований тег `vX.Y.Z` ставиться лише на коміт у `main` після злиття PR із зеленим CI.
2. На момент тегу файл `VERSION` = `X.Y.Z`. Підвищення версії йде окремим комітом у PR, а не після злиття. PR, що не змінює `VERSION`, тегу не потребує.
3. Повідомлення тегу: `vX.Y.Z: <опис> (#<Issue>, PR #<N>)`.
4. Опублікований тег не переносять і не видаляють. Виняток — тег на хибному коміті, від якого ще ніщо не залежить (аудит, звіт, реліз): його видаляють із записом в Issue.
5. Власник зберігає вето: незгода з тегом — коментар в Issue або PR чи мітка `blocked`.
6. Lead Engineer ставить тег **без окремої команди** одразу після злиття PR, що змінює `VERSION`, і повідомляє про це коментарем у PR. Інші теги — лише за командою власника.

Інцидент 2026-11-09: `v0.4.0` поставлено на стартовий коміт `5ba7fab` до злиття PR #26. Тег видалено за правилом 4 і поставлено на коміт злиття `c1b9d2f`.
