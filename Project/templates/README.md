# Шаблони документів і Work Products

* **Версія:** 0.1.1
* **Дата:** 2026-11-12
* **Тип WP:** Guide
* **Походження:** форми вихідного `docs/templates/`, що раніше були в
  `process/templates/` (#5); у NG єдине місце — `Project/templates/`.

Єдиний каталог шаблонів документів проєкту — `Project/templates/`.
Типи WP й правила їх розрізнення визначає
[конфігурація Work Products](../policies/work-products.md).

## 1. Вибір шаблону

* [Каталог за типами WP](work-products/README.md) — шаблони й пояснення
  покриття кожного типу, зокрема SYS/HW/SW вимог.
* [Report](report.md) — звіт про виконану роботу або експеримент.
* [Review Report](review.md) — рецензія; незалежність і прийняття
  визначають [правила рецензування](../policies/review-rules.md).
* [Шаблон PR](../../.github/pull_request_template.md) залишається в
  `.github/`, де його автоматично використовує GitHub. Це інтеграційна
  форма, а не другий каталог шаблонів WP.

Обирайте за призначенням, не за назвою файла. Вимоги можна зберігати
рядками таблиці або частиною Specification; Solution — пакетом
пов'язаних матеріалів. Окремі файли заради заповнення форми не потрібні.
Для багатофайлового WP визначте основний документ і зв'язки без копіювання
тієї самої інформації в кілька місць.

## 2. Застосування і підтримка

1. Замініть інструкції у квадратних/кутових дужках фактичними даними.
   Невідоме позначайте з причиною та відповідальним за уточнення.
2. Приберіть непридатні розділи з обґрунтуванням. Не видаляйте
   обмеження, негативні результати чи джерела задля позитивного висновку.
3. Перевірте посилання після копіювання: вони відносні до нового файла,
   не до шаблону. Вкажіть версію, історію та потрібні терміни.
4. Не видавайте заповнену форму за перевірений, погоджений або прийнятий
   результат. Зафіксуйте фактичний стан і потрібне рішення окремо.
5. Змінюючи шаблон, збережіть його призначення, поля й інструкції для
   читача, оновіть версію каталогу та посилання. Не переписуйте раніше
   створені звіти чи raw автоматично під нову форму.

`Template` — тип самих файлів-основ у цьому каталозі. Для нового шаблону
визначте цільовий WP, межі застосування, поля з підказками, історію
версій і терміни; додайте запис до каталогу. Окремий рекурсивний
«шаблон шаблону» не потрібний.

## 3. WP, для яких Markdown-форма не замінює сам артефакт

| Тип | Що фіксувати замість штучного документа |
|---|---|
| Data | Схему/одиниці, метод і час отримання, команди, джерельний SHA, середовище, перелік файлів і хеші, якщо застосовні. Сирі дані не перезаписувати; повтор — новий набір. Для експериментів діє [контракт походження](../tools/report-provenance.md). |
| Source Code | Реальний код у `Engineering/hw/`, `Engineering/sw/` або `Project/tools/`, його Git-версію, залежності/збірку та зв'язки з Design і перевірками. [Правила агента](../../AGENTS.md) та інструкції компонента визначають роботу з кодом; звіт не замінює код. |
| Configuration | Машиночитані налаштування, їхню схему/версію, ціль, залежності, спосіб застосування та перевірки. Секрети не зберігати. Склад пакета й точні версії описують за потреби через [Solution](work-products/solution.md) і [реєстр CI](../registers/configuration-items.md). |
| Hardware | Ідентичність плати/ревізії, схему й склад, інтерфейси, конфігурацію, умови використання та спосіб перевірки. У Git зберігають [Design](work-products/design.md), Configuration та докази, а не сам фізичний пристрій. Порядок доступу до стенда — у [правилах агента](../../AGENTS.md). |

Не додавайте метадані всередину незмінного стороннього джерела або
історичного raw. Їхнє походження описують у сусідньому маніфесті,
картці [Source](work-products/source.md) чи звіті.

## Абревіатури та глосарій

WP — Work Product; CI — елемент конфігурації; raw — сирі дані;
SHA — ідентифікатор Git-коміту або хеш із явно зазначеним алгоритмом.
