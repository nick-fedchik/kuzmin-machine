## 1. Призначення та рішення B3

**Decision B3-01 — погоджено власником Миколою Федчиком** для KPOL-CME-1
v0.1.0 на SHA `21a109eb4d1e962bf94d066207415c00e4d7576e`; рішення
зафіксовано в [PR #142](https://github.com/nick-fedchik/kuzmin-machine/pull/142#issuecomment-6825334563).
Це погоджує цільовий профіль, але не стверджує його реалізацію в #8,
завершення #19 або прийняття всієї архітектури S2.

| Варіант | Наслідки |
|---|---|
| Повний історичний KPOL | Потребує ще не визначених таймерів, каналів, планувальника, багатостанової атомарності та інших ABI; немає доказів підтримки. |
| KPOL-CME-1 — рекомендовано | Один активний концепт, одна подія, один стан і правило; можна окремо перевіряти синтаксис, семантику, діагностику й виконання без нового RTL-формату. |

Причина обмеження — не «усе інше неможливе», а відсутність установленого
відображення подій, кількох правил і атомарних записів кількох станів
у поточному CME. Це параметризований клас програм, **не дозвіл лише
двох текстів increase/decrease**. Імена, початкове значення, межа guard
і скінченні траси можуть відрізнятися.

Цей документ визначає **цільовий контракт для #8**, а не стверджує його
повне виконання компілятором та апаратною системою. У #150 реалізовано
окремий `profile="KPOL-CME-1"` і CLI; результати та межі —
у [Report](../../validation/kpol-cme/profile-150/report.md).
Безпрофільний API лишається експериментальним для сумісності.
У [#153 / Report](../../validation/kpol-cme/behavior-153/report.md)
перевірено задану поведінкову матрицю на direct, AXI/MMIO та зовнішньому
тригері AXI-обгортки; це скінченні RTL-симуляції, не HIL або доказ
еквівалентності всього домену.
Відомі дефекти з §7 робочого контракту
не стають правилами мови. Назва `KPOL-CME-1` — ID профілю, не KPOL v1.0.
No-Go історичного аудиту для повного стандарту v1.0 не скасовується.
Це похідна інженерна специфікація, не специфікація М. Ю. Кузьміна.

## 2. Синтаксис і статичні обмеження

Позначення `M`, `S`, `E`, `P`, `I`, `R` нижче — ідентифікатори;
повторення того самого позначення означає те саме ім'я. Лексика,
зарезервовані слова й коментарі — за §2 робочого контракту. Пробіли
не впливають на зміст. Дужки, що не змінюють AST виразу, дозволені.

```text
module = Problem M { Invariants { I : S >= 0 ; } }
         Solution M {
             state S : Int32 = initial ;
             event E ( P : Int32 ) ;
             rule R on E when guard { set S := S delta 1 ; }
         }
         [ Proof M { scenario+ } ]
guard = true | P < limit | P > limit | P == limit | P != limit
delta = + | -
scenario = scenario NAME { (step E ( P = integer ) ; | expect S == integer ;)+ }
```

`initial` — цілий літерал у `[0, 2147483647]`; `limit` і аргументи
подій — цілі літерали в `[-2147483648, 2147483647]`, з унарним `-`
для від'ємного значення. Decimal, Bool і Unknown не є такими літералами.
Порядок оголошень state/event неістотний; зайвих оголошень немає.
Відсутній `when` означає `true`, як у Parser. У Proof дозволено також
запис аргументу `P: integer`, який Parser нормалізує так само.
`expect` приймає Int32-літерал. Кожний scenario має принаймні один
`step` і один `expect`, після `step`; Proof не може бути порожнім.

Структурно рівно один `Invariant` має AST `S >= 0`. Він обов'язковий;
відсутність Invariants **не** означає відключення апаратної перевірки.
Рівно одне правило має рівно один запис саме в `S`. Імена не впливають
на opcode або інверсію: перейменування `Step` у `NotifyStep` не змінює
поведінку. Порядок імен не кодує семантики.

### 2.1. Явно відхилені конструкції

Усе, що не дозволено вище, відхиляється до емісії. Зокрема:

| Конструкція | Доля в KPOL-CME-1 / причина |
|---|---|
| `set S := 42`, `set S := P` та інші ASSIGN | Відхилити; поточний ASSIGN бере event_param, не константу. |
| `when false`, `not`, `and/or`, guard на стан, `>=`/`<=` | Відхилити; не замінювати на NOP/RANGE, інший операнд або інверсію за іменем. |
| Два правила для одного стану, кілька дій, кілька станів/подій | Відхилити весь модуль, не обирати перше правило й не розбивати транзакцію мовчки. |
| ADD/SUB з кроком, відмінним від 1 | Відхилити; спільне поле операнда guard/action ще не розділене. |
| Інші Invariants; Assumptions, Hazards, Alerts, Goals | Відхилити в цьому профілі; їхня референсна підтримка не є підтримкою CME. |
| Bool/U32/U64/Float/Pin, Unknown | Відхилити у виконуваних деклараціях; немає відповідного ABI цього профілю. |
| `change`, `on reject`, `covers`, cascade_map | Відхилити; підписки й каскади не є частиною KPOL-CME-1. |
| Proof/assert, порожній Proof, обчислювані payload/expect | Відхилити в цьому профілі; дозволено лише скінченні scenario вище. |
| Таймери, channels/CSP, namespace/import, linker, HMAC-контейнер, `.kmc` | Не входять до профілю або сирого ABI; не ігнорувати як «коментарі». |

Це обмеження **цільового CME-профілю**, не вилучення можливостей
референсного Interpreter. Для фронтенду та позапрофільних API чинним
описом залишається робочий контракт.

## 3. Семантика й спостережуваний результат

Подія `E` має рівно один відомий параметр Int32. Зовнішня прив'язка
передає `E(P=v)` як `(cid=0, param=32-бітне представлення v)`.
Невідоме ім'я події, зайвий/відсутній параметр, Unknown, значення поза
Int32 або звернення до іншого CID мають відхилятися **до подачі в PL**.
Нуль є відомим допустимим payload, не ознакою відсутності значення:
зовнішній тригер не підміняє його значенням MMIO-регістра або одиницею.
Бінарний образ не містить цих імен і не може перевірити payload сам.
Розміщення вхідного валідатора уточнюється в B1/B2; наявність такого
валідатора зараз не стверджується.

Для старого стану `s` і payload `p` guard обчислюється над **p**,
а не над s. Якщо guard хибний, стан залишається s. Якщо істинний,
кандидат `c = s + 1` або `s - 1` обчислюється математично.
Лише `0 <= c <= 2147483647` може стати новим станом. Негативний
кандидат або вихід із Int32 не повинен комітити обгорнуте значення.
Усі події виконуються послідовно, наступна починає оброблятися після
завершення попередньої; політика навантаження/втрат — не B3, а B5.

**Межа зіставлення:** порівнюють початковий стан і стан після кожної
події, а не лише останнє значення. Хибний rule guard у Interpreter
дає відсутність запису; у CME він дає `rejected_o`. Це **не**
еквівалентні журнали відмов. Помилка нормалізації Int32 у Interpreter
може підняти `KpolError`; у PL очікується відмова без зміни BRAM.
Порівняння числового стану застосовують до трас без такої помилки;
граничну відмову перевіряють окремо, не називаючи її однаковою
діагностикою frontend/RTL.

Proof виконується тільки на хості; щонайменше одна перевірка й усі
`expect` мають пройти, якщо Proof заданий. Його відсутність не є
підтвердженням коректності. Proof не емітується в образ і не замінює
поведінкову перевірку RTL або універсальний математичний доказ.

## 4. ABI CME-RAW-1

Цільовий споживач — `km_autonomous_sequencer` →
`km_concept_micro_engine` → `kpol_txn_gate_v2` у конфігурації CFG-P,
`DATA_WIDTH=32`. Точна база всіх локаторів — SHA у шапці; історична
база не оголошується майбутньою прийнятою FPGA-збіркою.

Образ — рівно **1024 байти**, 64 слоти по 16, без заголовка.
Активний лише слот CID 0. Порядок слів W0, W1, W2, W3; кожне слово
little-endian. Адреса байта — `16*cid + offset`, адреса 32-бітного
слова BRAM — `4*cid + word_index`; не плутати байтовий offset
AXI з індексом слова порту BRAM.

| Байти / біти дескриптора | Поле | KPOL-CME-1 |
|---|---|---|
| 0–3 / `[31:0]` | W0 current_state | initial; надалі змінюється лише цей стан. |
| 4–7 / `[63:32]` | W1 operand_val | limit у two's complement; для `true` — 0. |
| 8 / `[71:64]` | pred_opcode | `true`: 00; `==`: 01; `!=`: 02; `>`: 03; `<`: 04. |
| 9 / `[79:72]` | guard_flags | 03: assumption known=1, invariant known=1; решта бітів 0. |
| 10 / `[87:80]` | hazard_limit | 00; hazards не дозволені. |
| 11 / `[95:88]` | action_opcode | 01 INC або 02 DEC. |
| 12–15 / `[127:96]` | W3 subscriber_cid | 0 — каскаду немає. |

Усі байти слотів 1–63 дорівнюють нулю; **це не інструкції безпечного
NOP**. До них не можна подавати події: валідація CID — відповідальність
інтеграції, не наслідок заповнення нулями. ABI підтримує лише один
активний концепт цього профілю, хоча фізичний пул має 64 слоти.

`guard_flags` біти 0 і 1 означають відомість, не необов'язковість
перевірки: нуль дає fail-closed. INC/DEC не використовують operand,
тому немає колізії кроку з межею guard. GT/LT — signed Int32.
RANGE, BITMASK, ASSIGN, ADD, SUB та біти 2/3 **існують у RTL**,
але не дозволені в цьому профілі.

`ConceptMicroDescriptor.pack` пакує `<IIII>`;
`disassemble_concept_microcode` має відновити поля без втрат.
`compile_bram_image` — інша історична таблиця метаданих такого самого
розміру, **не CME-RAW-1**. `compile_signed_bram_image` з заголовком —
інший контейнер; завантаження його перших 1024 байтів як CME заборонене.
Довжина сама по собі не встановлює типу довільного файла; перевірку
походження й дозволених доступів визначає B4/#133.

У суміжному [контракті loader B4, §4](../hw/kpol-image-loader-pipeline-contract.md#4-контракт-формату-виконуваного-образу-format--memory-layout)
виправлено опис W2 до цього самого фактичного пакування. Це усунення
суперечності документації, не новий формат, не зміна RTL або фаз B4.

## 5. Вимоги до компілятора й діагностики

Усі B3-REQ — **кандидати**, пріоритет P1, походження G1/N2 і WI #19.
Вони задають цільові перевірки для реалізації #8; погодження профілю
не свідчить, що ці перевірки вже пройдено.
Уточнення #150 трасується через [Requirement KPOL](../../requirements/kpol.md);
граматику погодженого профілю не розширено за новими RFC.

| ID | Перевірний контракт / обґрунтування |
|---|---|
| B3-REQ-01 | Приймати лише граматику й обмеження §2; невідоме не ігнорувати. Імена не впливають на семантику. |
| B3-REQ-02 | Для дозволеного входу емітувати CME-RAW-1 за §4 без ручного RTL. Дані й opcode мають зберігати переходи §3; лише успішне пакування цього не доводить. |
| B3-REQ-03 | Будь-яке порушення профілю завершується діагностикою до створення вихідного файла; жодного «кращого наближення», мовчазного нуля `_eval_int` або вибору першого правила. |
| B3-REQ-04 | Відрізняти синтаксичну/типову помилку frontend від непідтриманої backend-конструкції. Діагностика містить код, ім'я/місце конструкції та причину; CLI повертає ненульовий код і не змінює наявний образ. |
| B3-REQ-05 | За наявності Proof виконати його до емісії: `total_checks > 0`, `passed_checks == total_checks`, без failures; це перевірка заданих сценаріїв, не довільної траси. |
| B3-REQ-06 | Підтвердити переходи й відмови за §3 поведінковими тестами, включно з межами, перейменуванням, direct/AXI. Не називати ці симуляції HIL і не переносити їх висновки на інші CFG. |

Класи діагностики профільного CLI в #150:
`B3-SYNTAX`, `B3-TYPE`, `B3-SHAPE` (кількість декларацій/правил/дій),
`B3-GUARD`, `B3-ACTION`, `B3-INVARIANT`, `B3-PROOF`.
Додатково `B3-PROFILE` — невідомий профіль API,
`B3-ACL` — відмова чинної ACL-перевірки, `B3-IO` — читання/створення файла.
Помилки типів, у тому числі аргументи Proof поза Int32, належать
`B3-TYPE`; коректно типізований, але позапрофільний Proof — `B3-PROOF`.
Перевіряльник повідомляє хоча б першу конкретну причину; накопичення
всіх помилок не вимагається. Неможливість створити новий файл — окрема
I/O-помилка, не «непідтримана мова».

## 7. Приймальні сценарії для #8

Це задані очікування регресій; фактичні результати матриці #153 —
у [Report](../../validation/kpol-cme/behavior-153/report.md).
Статичні відмови перевіряє також #150. Це не доказ усіх можливих трас.
Сценарії виконують на direct і AXI з тим самим RTL; після кожної події
перевіряють W0 і відсутність зміни W1–W3. Тести мають падати на
негативному контролі (наприклад, перестановці INC/DEC).

| Вхід / дія | Очікуваний результат |
|---|---|
| Приклад CounterDemo §4 робочого контракту: 10, `<20`, INC, payload 5/25 | Стани 11/11; при DEC — 9/9. Це вже наявні скінченні симуляції. |
| Той самий AST з `Step` → `NotifyStep` | Байти образу й траса станів ті самі; не інвертувати guard через ім'я. |
| Для кожного `<`, `>`, `==`, `!=` межа 0; payload -1/0/1 на окремо ініціалізованому стані 10 | INC лише коли відповідне математичне порівняння істинне. |
| `true`, INC: initial=2147483646, дві події | Перший стан 2147483647; друга подія не комітить overflow, W0 незмінне. Референс на другій події може дати `KpolError`, що фіксують окремо. |
| `true`, DEC: initial=1, дві події | Стани 0/0; друга відхилена за invariant, без запису -1. |
| `set S:=42`; `when false`; друге правило на S | Кожний модуль відхилено цілком до емісії з конкретною причиною. |
| Guard `S<20`, `P>=5`, `S+P`, відсутній/інший invariant | Відмова, не мовчазна зміна семантики. |
| Хибний/порожній Proof; existing output file | Жодного нового/зміненого образу; конкретна Proof або I/O діагностика. |
| Зовнішня подія з payload=0, MMIO-регістр містить інше число | Guard використовує саме 0; не fallback MMIO або 1. |

## 8. Походження, архів і умови завершення

Історичні v0.1–v0.9 — [Git-архів](https://github.com/nick-fedchik/kuzmin-machine/blob/707fdba697d92ef9874c9013eb6f4f3cb2796d70/specs/kpol/history.md), не дев'ять чинних
нормативних специфікацій. Навігаційні записи зберігають старі шляхи;
повний текст і первинне походження — за immutable SHA. Регресійні
приклади v0.1 збережено окремими незміненими fixtures, не переозначено
як програми KPOL-CME-1.

Для завершення #19 потрібні: цей Specification/Decision/матриця,
перевірене архівування, Report, рецензія іншого рецензента та явне
прийняття власником B3-01 з версією/SHA. Поточний автор не видає
собі Review Report. Прийняття специфікації **не означає** виконання
B3-REQ компілятором, закриття #8/#5 або досягнення MVP/TRL 4.
