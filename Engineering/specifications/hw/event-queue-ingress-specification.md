## 1. Призначення і межі

### 1.1. Проблема та контекст
У секвенсері [`km_autonomous_sequencer.sv`](../../hw/rtl/core/km_autonomous_sequencer.sv) реалізовано внутрішню чергу FIFO глибиною 16 слів (`fifo_count_q < 16`), тоді як у ранніх планах PoC фігурувало число 64. Досі жодне з цих значень не було підтверджене аналізом навантаження та узгодженою системною потребою.

Крім того, в поточному коді при досягненні 16 елементів умова `if (hw_trigger_valid_i && (fifo_count_q < 16))` просто ігнорує нові імпульси:
- Відсутній сигнал готовності/зворотного тиску (`ready_o` / backpressure) для зовнішнього джерела;
- Відсутня апаратна фіксація факту відкидання події (мовчазна втрата — silent drop);
- Не формалізовано арбітраж між одночасним надходженням зовнішнього тригера та внутрішнього каскаду від `km_concept_micro_engine`.

**Мета специфікації:** формалізувати архітектурне рішення **B5** ([`../../architecture/s2-candidate-system.md`, §7.1](../../design/s2-candidate-system.md#71-пять-рішень-для-погодження)), встановити правила приймання подій, арбітражу, політику переповнення черги без мовчазних втрат, та обґрунтувати параметризацію апаратних ресурсів FIFO.

### 1.2. Межі
- **Що специфікується:** Критерій «подію прийнято», правила впорядкування, пріоритети каскаду проти зовнішнього стимулу, поєднання handshake та явного обліку втрат, параметризація глибини черги, верифікаційний протокол стрес-тестування.
- **Що не входить:** Безпосередня модифікація RTL-коду (реалізується окремим Task після погодження), довільні абстрактні бенчмарки з максимального заповнення FPGA.

## 2. Архітектурне рішення B5 (Decision ADR-B5)

* **Статус:** Рекомендовано розробником, очікує підтвердження власника проєкту.
* **Питання:** Яке навантаження є цільовим і яка поведінка повинна забезпечуватися при зайнятості та переповненні черги FIFO?

### 2.1. Варіанти політики переповнення
1. **Варіант 1 (Мовчазне відкидання — Silent Drop):** Нові події ігноруються без зміни стану лічильників та сигналізації.
   - *Висновок:* **Категорично неприпустимо** для систем реального часу та функційної безпеки (ISO 26262), оскільки створює приховану відмову без можливості діагностики.
2. **Варіант 2 (Апаратний зворотний тиск — Backpressure / Handshake):** Виставляти `ready_o = 0` при `fifo_count_q == QUEUE_DEPTH`.
   - *Перевага:* Запобігає втратам у синхронних шинних протоколах (AXI Stream / DMA).
   - *Обмеження:* Фізичні асинхронні датчики або кнопки не можуть бути «призупинені» сигналом backpressure.
3. **Варіант 3 (Гібридна політика — Handshake + Non-Silent Drop з обліком — РЕКОМЕНДОВАНО):**
   - Модуль надає сигнал зворотного тиску `hw_trigger_ready_o = (fifo_count_q < QUEUE_DEPTH)`;
   - Якщо зовнішнє джерело ігнорує `ready_o == 0` і надсилає імпульс `valid`, подія **не записується** у переповнену пам'ять (захист цілісності BRAM/FIFO), але:
     1. Активується 1-тактовий строб `fifo_overflow_strobe_o`;
     2. Виставляється «липкий» (sticky) прапорець статусу `fifo_overflow_latched_o`;
     3. Інкрементується 32-бітний апаратний лічильник `events_dropped_count_o`;
     4. Спалахує попереджувальний індикатор на платі (`LED2`).

### 2.2. Обґрунтування глибини черги (16 проти 64)
- **Темп обробки конвеєра BRAM:** Як визначено в [`bram-pipeline-event-integration.md`](../../design/bram-pipeline-event-integration.md), час обробки одного концепту становить детерміновані 8 тактів ($80\text{ нс}$ при 100 МГц).
- **Сплескове навантаження (Burst Tolerance):**
  - Черга глибиною **$N = 16$** здатна поглинути пачку з 16 поспіль подій, що надходять кожен такт ($10\text{ нс}$, сумарний сплеск $160\text{ нс}$), згладжуючи пікове навантаження на період $16 \times 80\text{ нс} = 1.28\text{ мкс}$.
  - Глибина каскадних переходів KPOL у сценаріях MVP не перевищує 4–8 концептів.
- **Висновок щодо ресурсу:** Глибина 16 є повністю обґрунтованою та достатньою для MVP. Архітектура параметризується через `parameter int QUEUE_DEPTH = 16`, що дозволяє змінити глибину до 64 чи 256 під час синтезу для спеціалізованих задач без зміни структури автомата.

## 3. Специфікація інтерфейсу та поведінки черги

### 3.1. Інтерфейсні сигнали черги секвенсера

```
                      +-----------------------------+
                      |   km_autonomous_sequencer   |
                      |                             |
hw_trigger_valid_i  ->| [Вхід зовнішньої події]     |-> hw_trigger_ready_o (Handshake)
hw_trigger_cid_i    ->| (CID 0..63)                 |-> fifo_overflow_o (Sticky flag)
hw_trigger_param_i  ->| (Дані 32 біти)              |-> events_dropped_count_o (32b)
                      |                             |
                      | [Внутрішній каскад від CME] |
cme_trigger_sub_i   ->| (subscriber_cid)            |-> fifo_count_o (Рівень черги)
                      +-----------------------------+
```

| Сигнал | Напрям | Розрядність | Призначення та поведінковий контракт |
| :--- | :---: | :---: | :--- |
| `clk` | In | 1 | Системний такт PL (100.0 МГц, 10 нс). |
| `rst_n` | In | 1 | Асинхронне скидання (активний низький рівень). При 0: `fifo_wr_ptr <= 0`, `fifo_rd_ptr <= 0`, `fifo_count <= 0`, `dropped_count <= 0`. |
| `hw_trigger_valid_i` | In | 1 | Строб зовнішньої події (тривалість 1 такт). |
| `hw_trigger_cid_i` | In | 6 | Ідентифікатор концепту події (0..63). |
| `hw_trigger_param_i` | In | 32 | Числовий параметр / аргумент події. |
| `hw_trigger_ready_o` | Out | 1 | Готовність черги прийняти зовнішню подію: `1` при `fifo_count < QUEUE_DEPTH`, `0` при заповненій черзі. |
| `fifo_full_o` | Out | 1 | Ознака повного заповнення черги (`fifo_count == QUEUE_DEPTH`). |
| `fifo_overflow_o` | Out | 1 | «Липкий» прапорець фіксації хоча б однієї спроби несанкціонованого запису в повну чергу. |
| `events_dropped_count_o`| Out | 32 | Кількість відхилених подій через переповнення черги (доступний через регістр AXI). |

### 3.2. Критерій «Подію прийнято» (Event Ingestion Criterion)
Подія вважається **успішно прийнятою в чергу**, якщо на позитивному фронті `clk` виконується логічна умова:
$$\text{Event\_Accepted} = \text{hw\_trigger\_valid\_i} \land \text{hw\_trigger\_ready\_o}$$
При цьому:
1. `fifo_cid_q[fifo_wr_ptr_q] <= hw_trigger_cid_i`;
2. `fifo_param_q[fifo_wr_ptr_q] <= hw_trigger_param_i`;
3. `fifo_wr_ptr_q <= (fifo_wr_ptr_q + 1) % QUEUE_DEPTH`;
4. `fifo_count_q <= fifo_count_q + 1` (якщо одночасно не відбувається вичитка автоматом).

### 3.3. Правило арбітражу: Каскад vs Зовнішня подія
Коли завершується виконання правила KPOL з підпискою, модуль CME виставляє строб `cme_trigger_subscriber`.
- **Пріоритет:** Внутрішня каскадна подія має **вищий пріоритет арбітражу**, оскільки вона є частиною атомарного розподіленого переходу станів KPOL (CSP-семантика).
- **Поведінка при колізії (одночасний каскад і зовнішній тригер на одному такті):**
  - Каскадна подія гарантовано записується в поточний вільний слот черги;
  - Якщо в черзі є другий вільний слот (`fifo_count_q <= QUEUE_DEPTH - 2`), зовнішня подія записується у наступний слот;
  - Якщо в черзі лишався лише 1 слот, зовнішній події повертається `ready_o = 0` (або фіксується overflow при порушенні протоколу handshake).

## 5. Проєкт протоколу граничних перевірок (Protocol)

### 5.1. Умови та об'єкт
- **Об'єкт:** Тестбенч секвенсера `Engineering/hw/tb/km_autonomous_sequencer_tb.sv` з оновленими портами контролю черги.
- **Інструменти:** Icarus Verilog (`iverilog -g2012`), SystemVerilog Assertions (`assert property`).

### 5.2. Сценарії граничних умов
1. **Граничний тест заповнення черги:**
   - Подача 16 подій поспіль при заблокованій вичитці автомата.
   - *Очікування:* `fifo_count` послідовно зростає від 0 до 16; на 16-му такті `hw_trigger_ready_o` падає в 0; `fifo_full_o` стає 1.
2. **Стрес-тест переповнення (Overflow Negative Control):**
   - Подача 17-ї та 18-ї подій при `hw_trigger_ready_o == 0`.
   - *Очікування:* Вказівник запису `fifo_wr_ptr_q` не змінюється; `events_dropped_count_o` стає рівним 2; перші 16 подій залишаються цілісними; виставляється `fifo_overflow_o`.
3. **Колізія каскаду та зовнішньої події:**
   - На такті переходу в `ST_CHECK_CASCADE` подається одночасний зовнішній тригер.
   - *Очікування:* Каскадний CID стає перед зовнішнім CID у черзі.
4. **Спустошення та відновлення готовності:**
   - Автомат послідовно вичитує всі події з черги.
   - *Очікування:* Коли `fifo_count` зменшується нижче 16, сигнал `hw_trigger_ready_o` негайно повертається в 1.
