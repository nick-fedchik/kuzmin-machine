## 1. Призначення і межі

### 1.1. Проблема та контекст
У секвенсері [`km_autonomous_sequencer.sv`](../../hw/rtl/core/km_autonomous_sequencer.sv) реалізовано внутрішню чергу FIFO глибиною 16 слів (`fifo_count_q < 16`), тоді як у ранніх планах PoC фігурувало число 64. Досі жодне з цих значень не було підтверджене аналізом навантаження та узгодженою системною потребою.

Поточний RTL уже надає `hw_trigger_ready_o`, `fifo_overflow_o` та
`events_dropped_count_o`. Але облік втрат не реалізує авторське очікування.
Ready враховує лише зайнятість, не резервування слота каскадом;
при колізії за одного слота зовнішня подія відкидається з лічильником.

**Мета специфікації:** уточнити B5 та перевірні критерії очікування без
втрат для керованих джерел. Це не затверджує конкретного RTL-рішення
або достатності глибини для невизначеного навантаження.

### 1.2. Межі
- **Що специфікується:** Критерій прийняття, утримання неприйнятої події, порядок, каскадний арбітраж, відокремлення порушення протоколу від штатного очікування.
- **Що не входить:** Безпосередня модифікація RTL-коду (реалізується окремим Task після погодження), довільні абстрактні бенчмарки з максимального заповнення FPGA.

## 2. Архітектурне рішення B5 (Decision ADR-B5)

* **Статус:** Рекомендовано розробником, очікує підтвердження власника проєкту.
* **Питання:** Яке навантаження є цільовим і яка поведінка повинна забезпечуватися при зайнятості та переповненні черги FIFO?

### 2.1. Варіанти політики переповнення
1. **Відкидання, мовчазне або діагностоване:** не виконує авторського правила очікування; колишня гібридна рекомендація v1.0.x замінена.
2. **Backpressure / утримання — цільовий варіант:** до прийняття джерело зберігає valid і payload; ready має враховувати каскадний арбітраж. Повна черга не повинна зупиняти споживача, який її розвантажує.
3. **Фізично незупинне джерело:** потрібні окремі буферизація, межа навантаження та реакція на перевантаження. Протокол керованого producer не доводить відсутності втрат на фізичному вході.

Конкретне pending-сховище та спосіб недопущення повторного commit
каскаду ще треба визначити до реалізації. Зняття ready саме собою
не розв'язує цих питань і не є доказом відсутності deadlock.

### 2.2. Обґрунтування глибини черги (16 проти 64)
16 — default поточного параметра `QUEUE_DEPTH`, не встановлений
системний мінімум чи достатність для MVP. Потрібні визначені burst/rate,
часи обслуговування, каскадний граф і stalls. Колишні числа 8 тактів,
4–8 концептів та похідний бюджет не мають тут перевіреного raw-доказу
й не використовуються як приймальний критерій.

## 3. Специфікація інтерфейсу та поведінки черги

### 3.1. Інтерфейсні сигнали черги секвенсера

```
                      +-----------------------------+
                      |   km_autonomous_sequencer   |
                      |                             |
hw_trigger_valid_i  ->| [Вхід зовнішньої події]     |-> hw_trigger_ready_o (Handshake)
hw_trigger_cid_i    ->| (CID 0..63)                 |-> fifo_overflow_o (Sticky flag)
hw_trigger_param_i  ->| (Дані 32 біти)              |-> events_dropped_count_o (32b)
                      |                             |
                      | [Внутрішній каскад від CME] |
                      | каскад CME (внутрішній запит)|
                      +-----------------------------+
```

| Сигнал | Напрям | Розрядність | Призначення та поведінковий контракт |
| :--- | :---: | :---: | :--- |
| `clk` | In | 1 | Системний такт PL (100.0 МГц, 10 нс). |
| `rst_n` | In | 1 | Асинхронне скидання (активний низький рівень). При 0: `fifo_wr_ptr <= 0`, `fifo_rd_ptr <= 0`, `fifo_count <= 0`, `dropped_count <= 0`. |
| `hw_trigger_valid_i` | In | 1 | У цільовому протоколі утримується разом із незмінним CID/payload до прийняття; це зміна старого стробового контракту. |
| `hw_trigger_cid_i` | In | 6 | Ідентифікатор концепту події (0..63). |
| `hw_trigger_param_i` | In | 32 | Числовий параметр / аргумент події. |
| `hw_trigger_ready_o` | Out | 1 | Цільова готовність гарантує слот саме зовнішній події після резервування каскаду; лише `fifo_count < QUEUE_DEPTH` недостатньо. |
| `fifo_full_o` | Out | 1 | Ознака повного заповнення черги (`fifo_count == QUEUE_DEPTH`). |
| `fifo_overflow_o` | Out | 1 | «Липкий» прапорець фіксації хоча б однієї спроби несанкціонованого запису в повну чергу. |
| `events_dropped_count_o`| Out | 32 | Кількість відхилених подій через переповнення черги (доступний через регістр AXI). |

### 3.2. Критерій «Подію прийнято» (Event Ingestion Criterion)
У **цільовому**, ще не реалізованому протоколі подія вважається прийнятою
на позитивному фронті `clk` за умовою:

$$
\text{Event\_Accepted} = \text{hw\_trigger\_valid\_i} \land \text{hw\_trigger\_ready\_o}
$$

Після такого фронту має бути рівно одне додавання, без дублювання
утримуваної події. За ready=0 утриманий valid не є втратою або
порушенням і сам собою не повинен збільшувати лічильник відкидань.
Очікувані зміни покажчиків:
1. `fifo_cid_q[fifo_wr_ptr_q] <= hw_trigger_cid_i`;
2. `fifo_param_q[fifo_wr_ptr_q] <= hw_trigger_param_i`;
3. `fifo_wr_ptr_q <= (fifo_wr_ptr_q + 1) % QUEUE_DEPTH`;
4. `fifo_count_q <= fifo_count_q + 1` (якщо одночасно не відбувається вичитка автоматом).

### 3.3. Правило арбітражу: Каскад vs Зовнішня подія
Коли завершується виконання правила KPOL з підпискою, модуль CME виставляє строб `cme_trigger_subscriber`.
- **Пріоритет:** Каскад додається перед одночасною зовнішньою подією; це не витіснення старих FIFO-записів, CSP чи атомарна розподілена транзакція.
- **Поведінка при колізії (одночасний каскад і зовнішній тригер на одному такті):**
  - Каскад займає доступний слот; якщо слота немає, його потрібно утримати до прийняття, без повторного commit;
  - Якщо в черзі є другий вільний слот (`fifo_count_q <= QUEUE_DEPTH - 2`), зовнішня подія записується у наступний слот;
  - Якщо лишився один слот, ready зовнішньому джерелу має бути 0 до фронту; воно утримує подію. Поточний RTL цьому ще не відповідає.

## 5. Проєкт протоколу граничних перевірок (Protocol)

### 5.1. Умови та об'єкт
- **Об'єкт:** Тестбенч секвенсера `Engineering/hw/tb/km_autonomous_sequencer_tb.sv` з оновленими портами контролю черги.
- **Інструменти:** Icarus Verilog (`iverilog -g2012`), SystemVerilog Assertions (`assert property`).

### 5.2. Сценарії граничних умов
1. **Граничний тест заповнення черги:**
   - Подача 16 подій поспіль при заблокованій вичитці автомата.
   - *Очікування:* `fifo_count` послідовно зростає від 0 до 16; на 16-му такті `hw_trigger_ready_o` падає в 0; `fifo_full_o` стає 1.
2. **Очікування при full:**
   - Утримання valid/CID/payload до появи ready; паралельне розвантаження черги.
   - *Очікування:* Утримана подія не зникає, додається рівно один раз після прийняття; саме очікування не рахується відкиданням.
3. **Колізія каскаду та зовнішньої події:**
   - На такті commit (`ST_EVAL_GATE` поточного RTL) одночасно подати каскад та зовнішню подію за одного вільного слота.
   - *Очікування:* Каскадний CID додається першим, ready зовнішнього входу 0; зовнішня подія приймається пізніше без втрати. Окремо перевірити full-каскад та недопущення повторного commit.
4. **Спустошення та відновлення готовності:**
   - Автомат послідовно вичитує всі події з черги.
   - *Очікування:* Ready повертається в 1 за наявності слота для зовнішньої події після резервування каскаду; лише зменшення occupancy нижче 16 недостатньо.
