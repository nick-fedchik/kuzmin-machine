# EKPOL: позначка за третє відвідування

У читацькій картці рахуємо відвідування. На третє даємо відзнаку. На четверте — вже ні. Для цього потрібні дві комірки: одна рахує візити, друга реагує на зміну першої. Таку комірку зі станом і правилами реакції в EKPOL називають **концептом**.

## Від зовнішньої події до підписки

**Підготовка.** Інструменти написані на Go (потрібен Go 1.22 або новіший). Один раз із кореня репозиторію зберіть їх і додайте до `PATH`: `kpolc` — компілятор і перевірка тестів, `vmk` — покроковий налагоджувач.

```sh
go build -C Engineering/sw/kpol-go -o kpolc ./cmd/kpolc
go build -C Engineering/sw/vmk-go -o vmk ./cmd/vmk
export PATH="$PWD/Engineering/sw/kpol-go:$PWD/Engineering/sw/vmk-go:$PATH"
```

Збережіть програму як `visits.ekpol` у корені репозиторію:

```ekpol
module VisitsCard;

concept Visits: i32 = 0 [>= 0] {
    on Visit(stamp) when stamp == 1 => Visits += 1 commit;
}

concept Badges: i32 = 0 [>= 0] {
    on change(Visits) when Visits == 3 => Badges += 1 commit;
}

test ThirdVisit {
    send Visits(1);
    send Visits(0);
    expect Visits == 1;
    send Visits(1);
    send Visits(1);
    expect Badges == 1;
    send Visits(1);
    expect Visits == 4;
    expect Badges == 1;
}
```

Прочитайте перше правило як речення: **на подію** `Visit(stamp)`, **якщо** `stamp == 1`, **додай** один візит і **зафіксуй** результат (`commit;`). `stamp` тут лише ознака відмітки: нуль не зараховує візит. `i32 = 0 [>= 0]` означає: знакове ціле, спочатку нуль, допустимі лише невід’ємні результати.

У другого правила немає зовнішньої кнопки «видати відзнаку». `on change(Visits)` — **підписка**: коли `Visits` змінився, перевір нове значення. Саме тому на третьому візиті перевірка бачить `3`, а не `2`. Якщо відмітку відхилили, стан не змінився й підписку не запускають.

## Звірте прогноз із виконанням

У правилі `Visit` — назва події, а в тесті `send Visits(1)` вказує, **куди** подати відмітку `1`: у комірку `Visits`. `expect` перевіряє, що залишилося в пам’яті. Спершу виконайте тест, потім зберіть образ пам’яті й перегляньте кроки між перевірками:

```sh
kpolc verify visits.ekpol
kpolc build visits.ekpol visits.bin
vmk --program visits.bin --trace-events '0:1,0:0,0:1,0:1,0:1'
```

Перша команда друкує `VisitsCard: 1 embedded tests passed`. Образ не зберігає імен, тому в трасі комірки названо за номерами: `C00` — `Visits`, `C01` — `Badges`. `0` перед двокрапкою — номер `Visits`, першого оголошеного концепту. У блоці `[BLOCK 3]` стежте за парою `(Visits, Badges)`: спочатку `(0, 0)`, потім **`(1, 0) → (1, 0) → (2, 0) → (3, 1) → (4, 1)`**. Для третього зарахованого візиту в трасі видно два записи: спочатку в `C00`, потім у `C01`. Обидва спричинені однією вхідною подією. Образ не перезаписується: перед повтором видаліть `visits.bin`.

**Змініть один знак.** Якщо замінити `Visits == 3` на `Visits >= 3`, чи пройде останній `expect`? Повторіть `kpolc verify visits.ekpol`: компілятор повідомить `EKPOL-PROOF-ERR` і завершиться з кодом `1`, бо за четвертий візит теж нараховано відзнаку. Для одноразової відзнаки поверніть `==`. Якщо ж хочете заохочувати *кожен* візит починаючи з третього, залиште `>=` і змініть останнє очікування на `2`.

## Як читати короткий запис

Поверніться до початкової програми з одноразовою відзнакою. У ній правило всередині `Badges` можна **замінити** коротким записом:

```ekpol
~ Visits :: Visits == 3 => Badges += 1 .
```

`~ Visits` читається як `on change(Visits)`, `::` — як `when`, а завершальна крапка тут відповідає `commit;`. Замініть рядок і повторіть `kpolc verify visits.ekpol`: тест так само проходить. Ту саму програму в ключовому записі покаже `kpolc to-ekpol --ekpol-style keyword visits.ekpol`, а в класичному KPOL — `kpolc to-kpol visits.ekpol`.

## Користування компілятором `kpolc`

Для `.ekpol` компілятор має п’ять команд. Збирання `kpolc` описано на початку цього посібника.

| Команда | Що робить | Результат |
|---|---|---|
| `kpolc check FILE` | Розбирає програму й перевіряє її на відповідність апаратному профілю. | `OK: VisitsCard: 2 concepts, 1 tests (EKPOL-B64)` |
| `kpolc verify FILE` | Виконує вбудовані блоки `test`. | `VisitsCard: 1 embedded tests passed`; код `1` — тест не пройшов |
| `kpolc build FILE IMAGE` | Будує образ `CME-RAW-1` розміром 1024 байти. Профіль `EKPOL-B64` обирається за розширенням. | Файл `IMAGE` |
| `kpolc to-kpol FILE` | Записує програму в класичному KPOL на стандартний вивід. | Текст `.kpol` |
| `kpolc to-ekpol [--ekpol-style symbolic\|keyword] FILE` | Переписує програму в обраному стилі EKPOL. | Текст `.ekpol` |

### Що приймає профіль `EKPOL-B64`

Апаратний виконавець приймає до 64 концептів типу `i32` (`int32`) з інваріантом `[>= 0]` і невід’ємним початковим значенням. Підписки утворюють граф без циклів, і кожен концепт будить щонайбільше один інший. `kpolc build visits.ekpol visits.bin --dump-concepts` показує слоти образу:

```text
CID  Name   W0           W1           Pred     Guard  Haz    Action  Subscriber
0    Visits 0            1            EQ       0x13   0      INC     1
1    Badges 0            3            EQ       0x03   0      INC     0
```

`CID` — номер слота (порядок оголошення), `W0` — початкове значення, `W1` — поріг порівняння, `Pred` і `Action` — умова й дія, `Subscriber` — слот, який цей слот будить: `Visits` будить `Badges`. Образ не зберігає імен, тому налагоджувач показує слоти як `C00`, `C01`.

### Трансляція й додаткові результати

```sh
kpolc build visits.ekpol visits.bin --emit-kpol visits.kpol --emit-ekpol visits_kw.ekpol --ekpol-style keyword
kpolc build visits.ekpol visits.bin --emit-c99 visits.c --emit-z3-cert visits.json
```

* `--emit-kpol` і `--emit-ekpol` записують ту саму програму в класичному KPOL і в EKPOL у стилі `symbolic` або `keyword`. Для цього прикладу образи всіх трьох записів збігаються байт у байт (клас програм, де це гарантовано, описано в [§10 специфікації EKPOL](../specifications/kpol/ekpol-formal-specification.md#10-трансляція-ekpol--kpol)). Класичний KPOL збирайте профілем `KPOL-CME-2`.
* `--emit-c99` і `--emit-z3-cert` створюють модуль C99 і сертифікат безпеки. Для них потрібен виконуваний `z3`; сертифікат має `"verdict": "VERIFIED"`.
* `build` не перезаписує файли: якщо вихідний файл уже є, буде `EKPOL-IO: visits.bin: File exists`.

### Програми, яких апаратура не приймає

Концептуальні конструкції — типи `f64`, `u64`, `bool`, початкове значення `_`, скидання після читання `-> => . Sum = 0` — виконує лише концептуальний режим налагоджувача (`vmk --mode conceptual`). `kpolc check` прийме такий текст, але скаже, що він не компілюється в B64: `OK: Sum: 1 concepts (conceptual constructs; not compilable to EKPOL-B64)`. `kpolc build` відмовить: `EKPOL-TYPE-ERR: concept 'Sum' has type Float, but CME-RAW-1 bram64 requires Int32`.

### Повідомлення про помилки

| Повідомлення | Як відтворити | Що робити |
|---|---|---|
| `EKPOL-SYNTAX-ERR: … is missing '=>' action arrow` | Прибрати `=>` перед дією у правилі `Visit`. | Поставте `=>` між умовою й дією. |
| `EKPOL-TYPE-ERR: concept 'Badges' has type U64, …` | Замінити `i32` на `u64`. | Для апаратного образу використовуйте `i32`. |
| `EKPOL-CYCLE-ERR: cyclic cascade subscription … (Visits -> Badges -> Visits)` | Підписати `Visits` на `change(Badges)`. | Розірвіть цикл: підписки мають іти в один бік. |
| `EKPOL-COLLISION-ERR: … shares one 32-bit W1 operand_val between guard literal and ADD/SUB step != 1` | Замінити `Visits += 1` на `Visits += 2`. | Слот має одне поле `W1`, а поріг `stamp == 1` і крок `+= 2` потребують його обидва. Залиште крок `1` або приберіть число з умови. |
| `EKPOL-PROOF-ERR: embedded test verification failed: …` | `Visits == 3` замінити на `Visits >= 3`. | Звірте `expect` з трасою; `kpolc verify` повертає код `1`. |

Код виходу `2` означає відхилений текст, помилку файлу чи використання, `1` — `verify` не пройшов, `0` — усе добре. Покрокове трасування образу виконує `vmk`.

## Короткий глосарій

- **Подія** — привід перевірити правило. **Умова** (`when`) — запитання з відповіддю «так» або «ні».
- **Каскад** — послідовність реакцій: запис у першу комірку дає привід перевірити правило другої.
