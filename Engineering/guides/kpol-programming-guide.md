# KPOL: пишемо правило для двох квитків

У касі залишилося два квитки. Запит на один квиток можна виконати, запит на п’ять — ні. Що станеться з третім покупцем, якщо кожен із трьох просить по одному? Напишемо програму, яка відрізняє *правильний запит* від *можливого продажу*.

## Перша програма

Збережіть код у файлі `tickets.kpol` у корені репозиторію:

```kpol
Problem Tickets {
    Invariants { Stock: Left >= 0; }
}
Solution Tickets {
    state Left: Int32 = 2;
    event Buy(count: Int32);
    rule SellOne on Buy when count == 1 {
        set Left := Left - 1;
    }
}
Proof Tickets {
    scenario FirstSale {
        step Buy(count = 5);
        expect Left == 2;
        step Buy(count = 1);
        expect Left == 1;
    }
}
```

Почніть читати із середнього блоку, `Solution`. Пам’ять каси — це одне ціле число `Left`, спочатку `2`. Ззовні надходить подія `Buy`, а в ній число `count`. Рядок `when count == 1` питає, чи покупець просить рівно один квиток. Подвійне `==` порівнює числа; `:=` у наступному рядку пропонує нове значення для запису.

Навіщо тоді `Problem`? Він задає межу, якої **результат** не має переступати: `Left >= 0`. Навіть коли запит пройшов перевірку `when`, машина не повинна записати `−1`. А `Proof` — сценарій із передбаченими результатами: `step` подає подію, `expect` перевіряє залишок. Успіх такого сценарію підтверджує його приклади, а не всі можливі продажі.

## Чотири запити

Із кореня репозиторію запустіть Python 3; плата не потрібна:

```sh
python3 Engineering/sw/kpol-ref/kpol_debugger.py --profile KPOL-CME-1 \
    --program tickets.kpol --trace-events '0:5,0:1,0:1,0:1'
```

У `0:5` нуль — номер нашої єдиної комірки, а `5` — запитана кількість квитків. У блоці `TRACE` знайдіть чотири рішення:

| Запит | Залишок до → після | Чому |
|---|---|---|
| 5 | 2 → 2 | `REJECT_GUARD`: каса не продає п’ять за один раз. |
| 1 | 2 → 1 | `COMMIT`: перший квиток продано. |
| 1 | 1 → 0 | `COMMIT`: нуль — допустимий залишок. |
| 1 | 0 → 0 | `REJECT_INVARIANT`: запит правильний, але квитків більше немає. |

**Змініть програму.** Додайте в кінець сценарію, після `expect Left == 1;`, ще один `step Buy(count = 1);` і `expect Left == 0;`. Повторіть команду. Потім навмисно напишіть `expect Left == 1;` замість останнього нуля. Тепер сценарій не пройде і програма не дійде до трасування. Щоб виправити тест, відновіть `0`: змінювати умову продажу не потрібно.

## Короткий глосарій

- **Стан** живе між подіями (`Left`); **параметр** належить одному запиту (`count`).
- **Умова правила** перевіряє, чи слід виконати дію; **інваріант** — чи можна прийняти її результат.
