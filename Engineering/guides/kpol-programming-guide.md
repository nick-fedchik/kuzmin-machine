# Підручник з програмування мовою KPOL

У касі залишилося два квитки. Троє покупців просять по одному. Першим двом треба видати квиток, а після третього запиту залишок усе ще має бути нуль. Звідки програма знатиме, коли відняти одиницю, а коли залишити число без змін?

У KPOL програміст задає **що пам’ятати**, **на що реагувати** і **який результат дозволено зберегти**. Зовнішні події надходять уже після того, як програму описано. Тут немає `main`, який треба викликати для першого продажу.

**Маршрут:** [перша програма](#1-перша-програма) → [запис мови](#2-як-читати-й-писати-рядок) → [типи й вирази](#3-значення-типи-й-вирази) → [одночасні записи](#4-коли-два-записи-становлять-одну-дію) → [реакція на зміну](#5-як-одна-подія-будить-інше-правило) → [вимоги та відмови](#6-як-описувати-вимоги-й-відмови) → [перевірка й самостійна робота](#7-як-перевірити-свою-програму) → [користування компілятором](#8-користування-компілятором-kpolc).

## 1. Перша програма

**Підготовка.** Компілятор і налагоджувач написані на Go (потрібен Go 1.22 або новіший; плата не потрібна). Один раз із кореня репозиторію зберіть обидва інструменти й додайте їх до `PATH`:

```sh
go build -C Engineering/sw/kpol-go -o kpolc ./cmd/kpolc
go build -C Engineering/sw/vmk-go -o vmk ./cmd/vmk
export PATH="$PWD/Engineering/sw/kpol-go:$PWD/Engineering/sw/vmk-go:$PATH"
```

`kpolc` перевіряє програму, виконує її сценарії, запускає події й будує образ для апаратного виконавця. `vmk` показує, як виконавець обробляє події, крок за кроком.

Збережіть код у файлі `tickets.kpol` у корені репозиторію. Це повна програма. `Problem` описує умови задачі, `Solution` — стан і правила його зміни, `Proof` — приклади, на яких перевіряємо рішення.

```kpol
Problem Tickets {
    Invariants { Stock: Left >= 0; }
}
Solution Tickets {
    state Left: Int32 = 2;
    event Buy(count: Int32);
    rule SellOne on Buy when count == 1 {
        set Left := Left - 1;
    }
}
Proof Tickets {
    scenario FirstSale {
        step Buy(count = 5);
        expect Left == 2;
        step Buy(count = 1);
        expect Left == 1;
    }
}
```

Почніть читати із середнього блоку, `Solution`. Пам’ять каси — це одне ціле число `Left`, спочатку `2`. Ззовні надходить подія `Buy`, а в ній число `count`. Рядок `when count == 1` питає, чи покупець просить рівно один квиток. Подвійне `==` порівнює числа; `:=` у наступному рядку пропонує нове значення для запису.

Навіщо тоді `Problem`? Він задає межу, якої **результат** не має переступати: `Left >= 0`. Навіть коли запит пройшов перевірку `when`, машина не повинна записати `−1`. А `Proof` — сценарій із передбаченими результатами: `step` подає подію, `expect` перевіряє залишок. Успіх такого сценарію підтверджує його приклади, а не всі можливі продажі.

### Чотири запити

Спершу перевірте сценарій із блоку `Proof`, потім зберіть образ пам’яті виконавця й подайте йому чотири події:

```sh
kpolc verify tickets.kpol
kpolc build --profile KPOL-CME-1 tickets.kpol tickets.bin
vmk --program tickets.bin --trace-events '0:5,0:1,0:1,0:1'
```

Перша команда друкує `Tickets: 2/2 checks passed`. Образ `tickets.bin` не зберігає імен, тому в трасі комірку названо `Concept_0`. У `0:5` нуль — номер нашої єдиної комірки (перший оголошений стан), а `5` — запитана кількість квитків. Файл образу вже не перезаписується: перед повтором видаліть його. У блоці `[BLOCK 3]` знайдіть чотири рішення:

| Запит | Залишок до → після | Чому |
|---|---|---|
| 5 | 2 → 2 | `REJECT_GUARD`: каса не продає п’ять за один раз. |
| 1 | 2 → 1 | `COMMIT`: перший квиток продано. |
| 1 | 1 → 0 | `COMMIT`: нуль — допустимий залишок. |
| 1 | 0 → 0 | `REJECT_INVARIANT`: запит правильний, але квитків більше немає. |

**Змініть програму.** Додайте в кінець сценарію, після `expect Left == 1;`, ще один `step Buy(count = 1);` і `expect Left == 0;`. Повторіть `kpolc verify tickets.kpol`: тепер `Tickets: 3/3 checks passed`. Потім навмисно напишіть `expect Left == 1;` замість останнього нуля. Команда надрукує `FAIL FirstSale: Expectation failed at step 6 …` і завершиться з кодом `1`, а `kpolc build` відмовиться будувати образ: профіль `KPOL-CME-1` вимагає, щоб `Proof` проходив. Щоб виправити тест, відновіть `0`: змінювати умову продажу не потрібно.

## 2. Як читати й писати рядок

Розберімо `state Left: Int32 = 2;` по частинах. `state` каже, *що оголошуємо*: місце для значення, яке переживе обробку одного запиту. `Left` — вибране нами ім’я. Після `:` пишемо тип, тут `Int32` — ціле зі знаком. `= 2` задає початкове значення. `;` завершує оголошення, а не означає «перейти до продажу».

| Як записати | Як прочитати |
|---|---|
| `event Buy(count: Int32);` | Оголосити вид події. `Buy` — її ім’я; у дужках перелік іменованих параметрів з типами, тут один. Саме оголошення нічого не продає. |
| `rule SellOne on Buy` | Дати правилу ім’я `SellOne` і прив’язати його до **події** `Buy`. Ім’я правила не треба викликати. |
| `when count == 1` | Перевірити умову для *цього* правила. Якщо `when` пропустити, правило реагуватиме без додаткової умови. |
| `{ set Left := Left - 1; }` | Між фігурними дужками — дії правила. Ліворуч від `:=` — оголошений стан, праворуч — вираз для нового значення. |
| `Stock: Left >= 0;` | У секції `Invariants` ім’я перед `:` називає вимогу; праворуч — твердження, а не присвоєння. Це ім’я побачимо у повідомленні про порушення. |
| `step Buy(count = 1);` | У сценарії подати подію з конкретним аргументом. Тут `=` зв’язує ім’я параметра зі значенням; це не `==` у порівнянні й не `:=` у дії. |

Імена в прикладах починаються з латинської літери; далі можна вживати латинські літери, цифри й `_`. Початкове `_` також дозволене. Регістр важливий: `Left` і `left` — різні імена. `rule`, `when`, `Int32` — слова мови, не назви для власних змінних. Пробіли й відступи допомагають читати, але межі блока задають `{ }`. Коментар до кінця рядка почніть з `#` або `//`, багаторядковий візьміть у `/* … */`.

Модуль — одна задача в одному тексті: спочатку `Problem`, за ним `Solution`, далі, за потреби, `Proof`; ім’я після кожного з них **однакове**. Для події без даних пишіть `event Swap();`: дужки потрібні й тоді, коли вони порожні. У правилах, навпаки, пишіть `on Swap`, а не `on Swap()`.

**Де видно ім’я?** `Left` можна читати в різних правилах. `count` існує тільки в контексті `Buy`; його не можна читати у сценарному `expect` чи правилі іншої події. Якщо число потрібне після продажу, заведіть для нього стан. Не називайте параметр так само, як стан. Початкове значення одного стану може посилатись лише на стани, оголошені раніше.

## 3. Значення, типи й вирази

Тип відповідає на запитання «що тут можна зберегти й що з цим можна робити?». У касі залишок — число, а ознака «потрібна ручна перевірка» — відповідь «так» або «ні». Додавати одиницю є сенс до залишку, не до відповіді.

| Тип | Приклад оголошення стану | Навіщо він |
|---|---|---|
| `Bool` | `state Open: Bool = true;` | Логічні значення `true` і `false`; саме таку відповідь має давати умова. |
| `Int32` | `state Balance: Int32 = -2;` | Ціле від −2³¹ до 2³¹−1. |
| `U32`, `U64` | `state Visits: U32 = 0;` | Невід’ємні цілі 32 або 64 біт. Значення `-1` не поміститься; від’ємний залишок не «обернеться» у велике додатне число. |
| `Float<одиниця>` | `state Delay: Float<ms> = 2.5;` | Число з одиницею вимірювання. Наприклад, вольти, помножені на ампери, дають вати. Це не дозвіл складати вольти із секундами. |
| `Pin` | `state Lamp: Pin = 0;` | Рівень сигналу, `0` або `1`, а не довільний лічильник. Запис `Pin<…>` допускає іменовані позначки типу, але сам по собі не під’єднує фізичний контакт. |

Це типи **еталонного інтерпретатора** — програми, яка виконує правила мови на комп’ютері (`kpolc verify` і `kpolc run`). Першу касу ми будували в іншому режимі: `KPOL-CME-1` описує, що вміє конкретний апаратний виконавець. Не намагайтеся зібрати всі рядки таблиці для нього. Програми далі перевіряє й запускає інтерпретатор; команди наведено в §4.

Вираз будуємо зі значень, імен та операцій. `Left - count * 2` спочатку подвоює кількість, потім віднімає її від залишку. `(Left - count) * 2` робить інше. Порядок від сильнішого зв’язування до слабшого: унарні `-`, `not`; множення й ділення `* /`; додавання й віднімання `+ -`; порівняння `== != < <= > >=`; потім `and`, останнім `or`. `gcd(a, b)` обчислює найбільший спільний дільник для аргументів, сумісних із `U64`. Оператор `/` не є цілочисельним діленням: не записуйте його результат у цілий стан.

Напишіть умову «від одного до чотирьох включно» як `count >= 1 and count <= 4`. Математичне `1 <= count <= 4` тут не працює: результат першого порівняння вже логічний. Для «не один» годяться `count != 1` і `not (count == 1)`. Без дужок `not count == 1` спробує заперечити **число**.

**А якщо число не надійшло?** Нуль квитків — відома кількість. `Unknown` — значення невідоме. У параметрі події воно допустиме; в еталонному інтерпретаторі його не можна зберігати як стан. `count == Unknown` перевіряє саме відсутність значення. Порівняння `Unknown > 0` натомість дає `Unknown`, не `false`: невідомий охоронець правила перериває транзакцію. Запис `count != Unknown and count > 0` спершу перевіряє наявність числа і не обчислює праву частину, якщо числа немає.

**Спробуйте подумки.** Чи достатньо в першій касі замінити `when count == 1` на `when count > 0`, щоб продавати по два? Ні. Умова пропустить `2`, але `set Left := Left - 1;` усе одно відніме один. Для загального інтерпретатора потрібна дія `set Left := Left - count;`. Профіль `KPOL-CME-1` такої дії не підтримує.

## 4. Коли два записи становлять одну дію

На табло два числа. Треба поміняти їх місцями: `(2, 5)` має стати `(5, 2)`. У послідовному коді знадобилося б тимчасове місце, інакше перший запис знищив би одне з чисел. У KPOL обидва вирази праворуч від `:=` читають **один знімок стану до події**.

Збережіть цю окрему програму як `pair.kpol`:

```kpol
Problem Pair {}
Solution Pair {
    state A: Int32 = 2;
    state B: Int32 = 5;
    event Swap();
    rule Exchange on Swap {
        set A := B;
        set B := A;
    }
}
Proof Pair {
    scenario RoundTrip {
        step Swap();
        expect A == 5 and B == 2;
        step Swap();
        expect A == 2 and B == 5;
    }
}
```

Для цього та наступних файлів скористайтеся інтерпретатором: команда `kpolc verify` виконує блок `Proof`, а `kpolc run` подає окремі події. Виконуйте їх **з кореня репозиторію**.

```sh
kpolc verify pair.kpol
```

Результат `Pair: 2/2 checks passed` означає, що обидва `expect` справдилися. Поміняйте місцями два рядки `set`: результат не зміниться. А якщо замінити `set B := A;` на `set A := A;`, два рядки запропонують **різні** значення для `A`. Тоді не перемагає останній рядок: обидва записи скасовуються, і перша перевірка виявить старий стан `(2, 5)`. Так працює **транзакція**: узгоджені зміни приймаються разом або не приймається жодна. Причину відмови покаже `kpolc run pair.kpol -e 'Swap()'`: у рядку `diagnostics` буде `ConflictingWrites:A`.

## 5. Як одна подія будить інше правило

У читальній залі три місця. Працівник надсилає нове **загальне** число зайнятих місць, а табло має показувати кількість вільних. Нехай окреме правило оновлює табло після зміни лічильника. Тоді працівникові не треба знати, що табло взагалі існує.

`room.kpol`, повний приклад для інтерпретатора:

```kpol
Problem Room {
    Invariants { Capacity: Used >= 0 and Used <= 3; }
}
Solution Room {
    state Used: Int32 = 0;
    state Free: Int32 = 3;
    event Report(n: Int32);
    rule Record on Report { set Used := n; }
    rule UpdateBoard on change(Used) { set Free := 3 - Used; }
}
Proof Room {
    scenario Board {
        step Report(n = 2);
        expect Used == 2 and Free == 1;
        step Report(n = 4);
        expect Used == 2 and Free == 1;
    }
}
```

Виконайте `kpolc verify room.kpol`: `Room: 2/2 checks passed`. Щоб побачити каскад, подайте події: `kpolc run room.kpol -e 'Report(n=2)' -e 'Report(n=4)'`. На `Report(n = 2)` перша транзакція записує `Used = 2`. Через зміну `Used` інтерпретатор ставить у чергу **нову** подію для `on change(Used)`. Тепер правило табло бачить уже `2`, тож записує `Free = 1`. Лише після цих пов’язаних реакцій, тобто після **каскаду**, `expect` читає табло.

На `Report(n = 4)` перше правило пропонує неможливе значення. Вимога `Capacity` скасовує цей запис, `Used` не змінюється, подія для табло не виникає. Якщо подати `2` вдруге, запис допустимий, але зміни так само немає. **Особливість запуску:** на початку першого `run` інтерпретатор один раз ставить у чергу кожне оголошене спостереження `change`; тому табло може також обчислити початковий показ.

У повній мові можна написати `on change(A, B)`: привід для перевірки — зміна **хоча б одного** з перелічених станів. Ім’я `n` у такому правилі недоступне: це параметр зовнішнього `Report`, а не частина внутрішнього повідомлення про зміну. Для повторення роботи потрібна нова подія, не `while`. Правила, що без кінця змінюють стан одне одного, можуть вичерпати ліміт подій інтерпретатора; апаратний профіль `KPOL-CME-2` циклів підписок не приймає.

## 6. Як описувати вимоги й відмови

У бібліотеці дозволено бронювати до трьох книжок одним запитом. На запит про дві книжки варто звернути увагу, але це не причина його відхиляти. На чотири — не видавати нічого й позначити запит для ручної перевірки. Тут важливо розрізняти п’ять речей:

| Секція `Problem` | На яке запитання відповідає |
|---|---|
| `Assumptions` | Чи можна взагалі обробляти ці вхідні дані? Вимога з `on` діє для названої події; без `on` — лише під час ініціалізації. |
| `Hazards` | Чи є відома причина заблокувати подію? У звичайному режимі виконання спрацювання блокує звичайні правила цієї події. `to` вказує на логічний стан для ознаки небезпеки. |
| `Alerts` | Чи варто занести подію в журнал? Таке повідомлення саме по собі не забороняє видачу. |
| `Invariants` | Чи прийнятний стан одразу після запропонованих записів? Якщо ні, транзакцію скасовують. Умова має виконуватися й на старті. |
| `Goals` | Що хотілося б бачити після обробки черги? Невиконану ціль фіксують у звіті; це не відкат і не команда змінити стан. |

`loans.kpol` — повна програма для інтерпретатора:

```kpol
Problem Loans {
    Assumptions { Valid on Take: n != Unknown and n > 0; }
    Hazards { TooMany on Take to Review: n > 3; }
    Alerts { Large on Take: n == 2; }
    Invariants { Stock: Available >= 0; }
    Goals { Reserve: Available >= 1; }
}
Solution Loans {
    state Available: Int32 = 4;
    state Review: Bool = false;
    event Take(n: Int32);
    rule Lend on Take { set Available := Available - n; }
    rule Flag on reject Take when n > 3 covers TooMany {
        set Review := true;
    }
}
Proof Loans {
    assert Flagged on Take when n > 3 expect Review == true;
    scenario Requests {
        step Take(n = 2);
        expect Available == 2 and Review == false;
        step Take(n = 4);
        expect Available == 2 and Review == true;
        step Take(n = Unknown);
        expect Available == 2;
    }
}
```

Виконайте `kpolc verify loans.kpol`: `Loans: 6/6 checks passed`. Розберіть три кроки окремо:

1. `Take(2)` відповідає припущенню. `Large` потрапляє в журнал, проте `Lend` працює: лишається `2`.
2. `Take(4)` теж має відому додатну кількість, але спрацьовує `TooMany`. Замість `Lend` працює правило **відхиленої вхідної події** `on reject Take`. `covers TooMany` зв’язує його з конкретною вимогою: та сама подія, той самий вираз `n > 3` і дія `set Review := true;`. Це правило не є загальним обробником будь-якого скасованого `set`.
3. `Take(Unknown)` не проходить `Valid`. Кількість доступних книжок не зменшується. Тест перевіряє саме цей результат, а не прирівнює відсутню кількість до нуля.

Спробуйте четвертий запит `step Take(n = 3);` після першого. Він допустимий за кількістю, але результат видачі був би `−1`. Скасує його **`Stock`**, не `TooMany`; `Review` залишиться `false`. А запит на останні дві книжки законний і залишає нуль. У такому разі не виконано **ціль** `Reserve`, але книжки вже видані. Так можна вибрати правильну конструкцію: якщо нуль справді заборонений, змініть інваріант, а не ціль.

Щоб побачити **причини** цих рішень, виконайте для того самого модуля послідовність запитів `2, 3, 2`. Кожен `-e` — окремий запит:

```sh
kpolc run loans.kpol -e 'Take(n=2)' -e 'Take(n=3)' -e 'Take(n=2)'
```

Для кожного запиту `kpolc` друкує стан після каскаду й п’ять журналів: `hazards` — спрацьовані небезпеки, `alerts` — повідомлення, `rejected` — причини блокування події, `diagnostics` — скасовані записи та невизначені умови, `goals` — недосягнуті цілі. Для другого запиту побачите `state: Available=2 Review=false` і `diagnostics: InvariantViolation:Stock`; для третього — `Available=0`, `alerts: Large` і `goals: Reserve`. У першому випадку книжки залишилися, у другому — їх видано попри недосяжну ціль. `Take(n=Unknown)` покаже `rejected: RejectedInput:Take`: припущення `Valid` блокує подію.

## 7. Як перевірити свою програму

`scenario` — послідовність подій з відомого початкового стану. Кожен новий сценарій стартує **заново**, а кроки одного сценарію зберігають стан. `expect` читає стан після всього каскаду. `assert Flagged on Take when … expect …;` з попереднього прикладу застосовується до всіх кроків `Take` у сценаріях: `when` перевіряє стан і параметри **до** кроку, `expect` — **після**. Якщо жоден крок не зробив `when` істинним, перевірка повідомить `Vacuous assert`: властивість не була випробувана. Саме ім’я `Proof` не перетворює приклади на доведення для всіх входів.

**Самостійна задача.** На табло читальної зали потрібен також логічний напис «місць немає». Почніть із `room.kpol`. Що зберігати? На що реагувати? Як перевірити, що напис гасне, а не лише вмикається?

**Розв’язок.** Додайте в `Solution Room` стан `state Full: Bool = false;`. У тіло `UpdateBoard` після запису `Free` додайте `set Full := Used == 3;`. В окремому сценарії подайте `step Report(n = 3);` і перевірте `expect Full == true and Free == 0;`, потім подайте `step Report(n = 1);` і перевірте `expect Full == false and Free == 2;`. Спокусливий варіант `set Full := Free == 0;` на першому кроці дасть **неправильний** напис: це ще попереднє `Free` зі знімка. Візьміть `Used` або винесіть оновлення напису в окреме правило `on change(Free)`.

### Якщо результат не такий, як очікували

| Ознака | Де шукати помилку |
|---|---|
| Парсер не приймає рядок із `set` | Перевірте `:=`, крапку з комою й дужки. У KPOL не пишуть `=>` і `commit;` з EKPOL. |
| `unresolved name` | Перевірте регістр і область видимості. Параметр `Buy` не існує в правилі `on change(Left)`. |
| Після події жодного запису | Почніть із припущень і небезпек, далі перевірте `when`, можливий конфлікт записів та інваріант. `when false` пропускає одне правило, а не всі правила цієї події. |
| `kpolc verify` пройшов, а `kpolc build` каже `B3-SHAPE` або `CME2-SHAPE` | Перевірено поведінку в інтерпретаторі, не придатність для плати. `CME-1` — один `Int32` і крок `±1`; `CME-2` (`--profile KPOL-CME-2`) підтримує кілька станів та обмежені каскади, але не довільний `Solution`. |

## 8. Користування компілятором `kpolc`

Досі ми користувалися `kpolc` як перевіркою. Тепер зберемо його можливості докупи. `kpolc` робить п’ять справ над текстом KPOL: **перевіряє** його, **виконує** сценарії й події, **будує** образ пам’яті для апаратного виконавця, **транслює** в EKPOL і **генерує** C99. Як зібрати `kpolc`, описано на початку §1.

### 8.1. Команди для файлів `.kpol`

| Команда | Що робить | Результат |
|---|---|---|
| `kpolc check FILE` | Розбирає текст і перевіряє імена, типи й вимоги. | `OK: Tally: 2 states, 1 events, 2 rules, with Proof` |
| `kpolc verify FILE` | Виконує сценарії й `assert` блока `Proof`. | `Tally: 2/2 checks passed`; код `1`, якщо хоч одна перевірка не пройшла |
| `kpolc run FILE -e 'Подія(арг=значення)' …` | Подає події інтерпретатору; кожен `-e` — окремий запит. Значення: ціле, десяткове, `true`, `false`, `Unknown`. `--json` дає один рядок JSON на запит. | Стан і журнали після кожного запиту |
| `kpolc build [--profile П] FILE IMAGE` | Перевіряє програму на відповідність профілю й записує образ `CME-RAW-1` розміром 1024 байти. | Файл `IMAGE` |
| `kpolc to-ekpol [--ekpol-style symbolic\|keyword] FILE` | Записує програму в EKPOL на стандартний вивід. | Текст `.ekpol` |

`check`, `verify` і `run` розуміють **всю** мову KPOL. `build` строгіший: апаратний виконавець уміє менше, тому програма має вкластися в **профіль**.

### 8.2. Профілі: що приймає апаратний виконавець

Збережіть програму `tally.kpol`. Вона рахує додавання, а третє з них запускає друге правило:

```kpol
Problem Tally {
    Invariants { CountOk: Count >= 0; DoneOk: Done >= 0; }
}
Solution Tally {
    state Count: Int32 = 0;
    state Done: Int32 = 0;
    event Add(n: Int32);
    rule Collect on Add when n > 0 { set Count := Count + 1; }
    rule Mark on change(Count) when Count >= 3 { set Done := Done + 1; }
}
Proof Tally {
    scenario ThreeAdds {
        step Add(n = 1);
        step Add(n = 1);
        expect Done == 0;
        step Add(n = 1);
        expect Done == 1;
    }
}
```

`kpolc verify tally.kpol` проходить, але `kpolc build tally.kpol tally.bin` відмовляє: `B3-SHAPE: module Tally: expected exactly one state, event and rule`. За замовчуванням `build` використовує профіль `KPOL-CME-1`, а він приймає лише одну комірку. Оберіть багатокомірковий профіль:

```sh
kpolc build --profile KPOL-CME-2 tally.kpol tally.bin --dump-concepts
```

| Профіль | Що приймає | Типові коди відмови |
|---|---|---|
| `KPOL-CME-1` (за замовчуванням) | Один стан `Int32`, одна подія з одним параметром `Int32`, одне правило; інваріант `S >= 0`; дія `S + 1` або `S - 1`; охоронець порівнює параметр з числом. | `B3-SHAPE`, `B3-INVARIANT`, `B3-ACTION`, `B3-GUARD` |
| `KPOL-CME-2` | До 64 станів `Int32`; кожен має рівно одне правило — на подію або на `change(інший стан)`; кожен має інваріант `S >= 0`; каскад без циклів і розгалужень; дії `S + K`, `S - K`, присвоєння параметра. | `CME2-SHAPE`, `CME2-ACTION`, `CME2-CASCADE`, `CME2-OPERAND-COLLISION`, `CME2-RANGE` |

Обидва профілі вимагають непорожнього `Proof`, який проходить (`B3-PROOF`, `CME2-PROOF`). Точні умови — у [§7 специфікації KPOL](../specifications/kpol/kpol-formal-specification.md). Після `--dump-concepts` побачите таблицю слотів:

```text
CID  Name  W0           W1           Pred     Guard  Haz    Action  Subscriber
0    Count 0            0            GT       0x13   0      INC     1
1    Done  0            3            LT       0x0B   0      INC     0
```

Рядок — це 16-байтний слот образу. `CID` — номер слота (порядок оголошення станів), `W0` — початкове значення, `W1` — поріг або крок, `Pred` і `Action` — умова й дія, `Subscriber` — номер слота, який цей слот будить після зміни. `Count` будить `Done` (`Subscriber 1`). Умову `Count >= 3` апаратура записує як `< 3` з прапорцем інверсії: це біт `0x08` у `Guard`; `0x10` дозволяє каскад.

Образ не зберігає імен станів. Щоб побачити, як виконавець його обробляє, подайте три події налагоджувачу:

```sh
vmk --program tally.bin --trace-events '0:1,0:1,0:1'
```

У блоці `[BLOCK 3]` на кожну подію буде два кроки: `E0.0` — `COMMIT` у `Count` (`C00`), `E0.1` — реакція `Done` (`C01`). Для перших двох подій реакція дає `REJECT_GUARD`, бо `Count < 3`; на третій — `COMMIT *STATE_CHANGE(0->1)`.

### 8.3. Інші результати компіляції

```sh
kpolc build --profile KPOL-CME-2 --emit-ekpol tally.ekpol --ekpol-style keyword tally.kpol tally.bin
kpolc build --profile KPOL-CME-2 --emit-c99 tally.c --emit-z3-cert tally.json tally.kpol tally.bin
```

* `--emit-ekpol` записує ту саму програму в EKPOL (`symbolic` — стиснутий запис, `keyword` — слова `on`, `when`, `commit`). У блок `test` потрапляють лише очікування виду `Стан == число`; складніші (з `and`) транслятор пропускає. Перевіряйте їх `kpolc verify` над вихідним KPOL.
* `--emit-c99` записує модуль C99 для мікроконтролера; `--emit-z3-cert` — сертифікат безпеки (`"verdict": "VERIFIED"`, перевірки `P1`–`P4`). Для обох потрібен виконуваний `z3`: без нього команда завершується помилкою `…-C99`, а не мовчки пропускає перевірку.

`build` **ніколи не перезаписує** файли: якщо `tally.bin` уже є, буде `CME2-IO: tally.bin: File exists`. Якщо одна з вихідних операцій не вдалася, створені файли видаляються.

### 8.4. Коди виходу й повідомлення про помилки

| Код виходу | Значення |
|---|---|
| `0` | Усе виконано. |
| `1` | `verify`: хоча б одна перевірка `Proof` не пройшла. |
| `2` | Помилка використання, читання файлу або відхилений текст програми. |

| Повідомлення | Причина | Що робити |
|---|---|---|
| `FILE:РЯДОК:СТОВПЕЦЬ: expected ';', got '}'` (`build` додає префікс `B3-SYNTAX` або `CME2-SYNTAX`) | Синтаксична помилка. | Перейдіть до вказаного рядка й стовпця; частіше за все бракує `;`. |
| `unresolved name 'Total'` | Ім’я не оголошено у тій області, де його використано. | Перевірте регістр і область видимості (§2). |
| `FAIL ThreeAdds: Expectation failed at step 5: …` | `expect` не збігся з станом. Номер рахує всі `step` і `expect` сценарію. | Звірте очікування з результатом `kpolc run`. |
| `CME2-PROOF: … Proof failed …` | `build` відмовився будувати образ, бо `Proof` не проходить. | Спершу виправте сценарій командою `kpolc verify`. |
| `B3-SHAPE`, `CME2-SHAPE` | Програма коректна, але не вміщається в профіль. | Оберіть інший профіль або спростіть програму (§8.2). |
| `unknown input event 'Nope'`, `payload for 'Add' must contain exactly n` | `kpolc run` отримав невідому подію або не ті аргументи. | Імена аргументів мають збігатися з `event`. |

## Короткий глосарій

- **Стан** живе між подіями (`Left`); **параметр** належить одному запиту (`count`).
- **Охоронець** — умова `when`, яка обирає правило; **інваріант** — умова, яку має зберегти результат.
- **Транзакція** читає один знімок і приймає або скасовує записи разом; **каскад** продовжує роботу наступними транзакціями.

За [формальною специфікацією KPOL](../specifications/kpol/kpol-formal-specification.md) можна уточнити граматику (§3), типи (§5), виконання (§6) та точні межі профілів (§7). [Підручник KPOL-AUTH](kpol-auth-programming-guide.md) пояснює окрему авторську нотацію; [практикум EKPOL](ekpol-programming-guide.md) — ще один спосіб записати реакцію на подію.
