# Рішення B6: Гетерогенний симбіоз Машини Кузьміна та GPU для паралельного виконання підписок (Persistent Mega-Kernel)

* **Версія:** 0.3.1
* **Дата:** 2026-11-14
* **Тип WP:** Decision
* **Статус:** Запропоновано (Proposed; цільові числові показники підлягають HIL-верифікації за EXP-GPU-01).
* **Власник:** Микола Федчик; автор концепції — Микола Федчик.

## Контекст і питання

У конфігурації `CFG-P` Машини Кузьміна (МК) на ПЛІС час обробки однієї події детермінованим 8-тактовим скінченним автоматом (`km_autonomous_sequencer` @ 100 МГц) становить фіксовані $80\text{ нс}$ за порожньої вхідної черги з нульовим внутрішнім алгоритмічним джитером тактової сітки. Проте при масштабуванні системи на зовнішні підписники (консьюмери) виникає критичне «вузьке місце» (Callback Bottleneck):
1. Зовнішні фізичні мікроконтролери (MCU), підключені через послідовні шини (isolated UART, SPI, CAN), мають час реакції $10\dots 1000\ \mu\text{с}$, що на 2–4 порядки повільніше за ядро ПЛІС.
2. Розгортання десятків окремих мікросхем MCU для паралельної обробки підписок ускладнює схемотехніку друкованої плати, збільшує енергоспоживання та створює ризики десинхронізації шин.
3. Класичний запуск ядер GPU через виклики API хост-драйвера (`cudaLaunchKernel`) має власний накладний час диспетчеризації $3\dots 10\ \mu\text{с}$, що є неприйнятним для жорсткого реального часу.

Постає інженерне питання: як усунути затримку передачі та забезпечити масове паралельне виконання підписок подій без розсипу фізичних мікроконтролерів і без затримок запуску GPU-кернелів?

## Варіанти та рішення

Було розглянуто три альтернативні архітектурні варіанти:

1. **Варіант 1: Масив фізичних MCU на платі (Baseline).**  
   Розподіл підписників по окремих чіпах Cortex-M4/M7 через шини SPI/UART.  
   *Недоліки:* фізичні обмеження ліній зв'язку, висока латентність шини ($10\dots 100\ \mu\text{с}$), складне розведення трас, відсутність динамічного масштабування.

2. **Варіант 2: Дискретні запуски CUDA-кернелів на GPU за перериванням.**  
   ПЛІС генерує переривання IRQ хост-процесору, який викликає `cudaLaunchKernel`.  
   *Недоліки:* затримка контекстного перемикання ОС Linux та ініціалізації ядра GPU ($3\dots 10\ \mu\text{с}$), значний апаратний джитер ($\sigma > 1\ \mu\text{с}$).

3. **Варіант 3 (Обране рішення B6): Персистентний кернел на SM GPU (Persistent Mega-Kernel) + прямий трансфер у когерентний поштовий буфер (GPUDirect RDMA / System-Coherent DMA).**  
   Зовнішні периферійні інтерфейси (PCIe BAR1 / GPUDirect RDMA на дискретних GPU або системний DMA у когерентну Unified LPDDR5 на Jetson AGX Orin) не мають прямого адресного доступу до внутрішньої `SM Shared Memory` (`__shared__` SRAM). Тому обмін будується за двоступеневою схемою:
   - **Когерентна вхідна скринька подій (Coherent Event Mailbox):** ПЛІС формує зведений бітовий вектор подій (`Event Register`, 64–256 бітів) і без участі CPU записує його у вирівняну за кеш-лінією когерентну область пам'яті низької латентності GPU (`BAR1 VRAM` або системно-когерентна `Unified Memory`, що відображається через тканину `L2 Cache`).
   - **Резидентне виконання в SM:** Довготривалий варп-процес на мультипроцесорі GPU (SM) у циклі виконує атомарне `acquire`-читання поштової скриньки системної області видимості (`ld.global.acquire.sys` із попаданням у `L2` без повторної активації рядків DRAM на холостих ітераціях), тоді як усі змінні станів, коефіцієнти та таблиці диспетчеризації підписників постійно утримуються у регістровому файлі та внутрішній `Shared Memory` SM (`1–2` такти доступу).

## Наслідки

* **Очікувані позитивні наслідки (проєктні цільові межі до HIL-перевірки):**
  * Розрахунковий наскрізний час реакції масиву з 32–64 підписників становить цільові $0.5\dots 1.0\ \mu\text{с}$ (підлягає інструментальній перевірці в `EXP-GPU-01`), що на 2–3 порядки менше за типові затримки послідовних шин UART/CAN.
  * Усувається потреба в розсипі фізичних мікросхем MCU на платі; всі мікро-обчислювачі стають віртуальними потоками в єдиному пулі обчислювачів GPU.
  * Забезпечується відсутність викликів диспетчера ОС на кожну подію (Zero-CPU Dispatch).

* **Обмеження та ризики:**
  * **Warp Divergence:** підписники у межах одного варпа повинні мати однорідну обчислювальну структуру (поліноми, ПІД, лінійні фільтри); сильне розходження гілок коду спричиняє серіалізацію потоків варпа.
  * **I-Cache Trashing:** код нано-колбеків повинен бути компактним або параметризованим через таблиці даних (Data-driven execution).
  * Необхідність експериментальної верифікації на фізичному стенді (протокол [EXP-GPU-01](../../Research/studies/fpga-gpu-symbiosis/experiments/EXP-GPU-01/protocol.md) у складі дослідження [fpga-gpu-symbiosis](../../Research/studies/fpga-gpu-symbiosis/README.md) на платформі Seeed Studio J501 / Jetson AGX Orin).

## Специфікація обчислювальних ядер та інваріант пам'яті (Уточнення Федчика)

1. **Цільовий тип обчислювачів — Універсальні шейдерні АЛП (INT32/FP32):**
   * Для паралельного виконання коду підписників призначаються саме універсальні векторні/скалярні ядра: **CUDA Cores** (NVIDIA), **Stream Processors** (AMD) або **Xe Vector Engines** (Intel).
   * Спеціалізовані тензорні/матричні блоки (Tensor Cores / Matrix Cores) не використовуються, оскільки вони орієнтовані виключно на множення щільних матриць ($D = A \times B + C$) і непридатні для поодиноких скалярних обчислень, бітових масок та предикатної логіки.
   * Шейдерні АЛП надають критичні переваги:
     * Однотактові інструкції бітових операцій (`BFE`, `POPC`, `LOP3`);
     * Апаратне предикатне виконання (`SEL` / Predicated Execution), що дозволяє скасовувати операції неактивних підписників без накладних витрат умовних переходів `if/else` (запобігання Warp Divergence);
     * Тактова частота $1.3\dots 2.5\text{ ГГц}$, за якої розрахунок 15–20 інструкцій ПІД-регулятора триває лише $10\dots 20\text{ нс}$.

2. **Інваріант ієрархії пам'яті (розділення поштового буфера та робочого стану SM):**
   * Робочі змінні станів підписників, коефіцієнти регуляторів та таблиці маршрутизації повинні постійно утримуватися у внутрішньокристальній пам'яті SM — регістровому файлі або спільній пам'яті (`Shared Memory` / `Local Data Share` / `SLM`) із доступом за $1\dots 2\text{ такти}$.
   * Звернення до некешованої зовнішньої пам'яті (`VRAM` / `DRAM LPDDR5` із затримкою $200\dots 400\text{ тактів}$) під час обчислення тіла підписників заборонено; єдиним зовнішнім зверненням варпа є когерентне `acquire`-читання вхідної кеш-лінії `Event Mailbox` (через `L2`) та запис результуючого вектора виходів.

## Абревіатури та глосарій

* **ADR** — Architecture Decision Record (запис архітектурного рішення).
* **GPUDirect RDMA** — технологія прямого доступу периферійних контролерів до пам'яті GPU через шину без CPU.
* **MCU** — Microcontroller Unit (мікроконтролер).
* **Persistent Mega-Kernel** — постійно активний (без завершення й повторного запуску) варп-процес на шейдерних ядрах SM GPU, що в циклі виконує атомарне `acquire`-опитування зовнішньої когерентної вхідної скриньки подій (`Event Mailbox` у `BAR1 VRAM` / `Unified Memory`, через `L2`), тоді як робочий стан підписників (змінні, коефіцієнти, таблиці маршрутизації) постійно резидентно утримується окремо — у регістровому файлі та внутрішній `Shared Memory` SM, а не в самій поштовій скриньці.
* **Shared Memory** — внутрішньокристальна швидкісна пам'ять блоку SM у GPU з латентністю 1–2 такти.
* **Warp** — базова група з 32 апаратних потоків в архітектурі NVIDIA GPU.
* **Warp Divergence** — деградація швидкодії варпа при розходженні умовних переходів `if/else`.
