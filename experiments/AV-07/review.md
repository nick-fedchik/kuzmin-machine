# Рецензія на звіт AV-07 (рецензент: Copilot)

* **Версія:** 1.0.0 (рецензує версію 1.0 звіту). **Роль:** рецензент. **Конфлікт інтересів:** рецензент не є автором звіту, скриптів і сирих даних AV-07.
* **Звіт, що рецензується:** [`AV-07_Mutation_Testing_Report_UA.md`](report.md), коміт `20b63a9`. Автор — агент Gemini.
* **Підстава:** план, §4.2 (AV-07), §2, п. 7, §6.1.
* **Що перевірено:**
  * [`raw/av07_mutation_results.json`](raw/av07_mutation_results.json);
  * код [`run_av07_mutation.py`](scripts/run_av07_mutation.py);
  * RTL і тестбенчі, на які спрямовано мутанти;
  * базовий прогін: усі 7 тестбенчів на немутованому RTL (`iverilog -g2012` + `vvp`, той самий критерій «вбито», що й у скрипті).
* **Вердикт:** **не приймати.**
  * Сирі дані придатні. Головний результат експерименту — «тестбенчі `km_cascade_arbiter_engine` і частково `km_rcfc_engine` не ловлять дефектів» — правильний і цінний.
  * Розділ «Висновки» стверджує протилежне до таблиць. Звіт неправильно рахує мутанти, які не вдалося застосувати.
* **Перенесено з:** `drafts/KuzminMachine/04-verification-and-qa/Review_Reports/AV-07_Mutation_Testing_Review_Report_UA.md` @ `a4738bc` (2026-11-09)

## 1. Базова лінія (моя перевірка)

Скрипт не перевіряє, чи проходять тестбенчі на немутованому RTL. Якщо базовий прогін сам падав би за критерієм «вбито», усі KILLED були б хибними. Я перевірив це окремо: усі 7 тестбенчів на чистому RTL завершуються з `rc = 0`. Рядків `FAIL`, `mismatch`, `$fatal` у виводі немає. Отже, позначки KILLED у JSON достовірні. Цю перевірку варто вбудувати в скрипт.

## 2. Суттєві зауваження

**З1. Висновки суперечать даним.**

| Що каже звіт | Що в даних |
| :--- | :--- |
| Висновок 1: «усі тестбенчі… володіють **100 % чутливістю**» | Арбітр — 0/3; RCFC — 1/3 (точніше 1/2, див. З2) |
| Висновок 2: «жоден мутант не зміг вижити» | 4 мутанти пройшли симуляцію без виявлення; ще 2 не запускалися |
| Заголовок: «Mutation Score = 72,7 % (16/22)» | 16 / 20 = **80 %** застосованих; 2 мутанти — помилка інструменту |

Висновки, імовірно, написано до прогону за шаблоном. Їх треба переписати за даними.

**З2. Два «вижилі» мутанти насправді не застосовано.**

У JSON `MUT-RCFC-03` і `MUT-PIPE-03` мають статус `ERROR_TARGET_NOT_FOUND`. Скрипт їх не застосовував і не симулював. Але рядок рендеру звіту виводить будь-який не-KILLED статус як «SURVIVED (Тест пропустив дефект!)», а стадію — як `N/A`.

Причина в пробілах:

| Мутант | Ціль у скрипті | Рядок у RTL |
| :--- | :--- | :--- |
| `MUT-RCFC-03` | `result_q␣␣␣␣␣<= {16'd0, avalanche_processed_q};` | `km_rcfc_engine.sv:309` — `result_q␣<= …` |
| `MUT-PIPE-03` | `accum_sum_q␣␣␣␣␣␣␣<= accum_sum_q + …` | `km_stream_pipeline_engine.sv:238` — `accum_sum_q␣<= …` |

Наслідки:
- зведена таблиця (рядки 18–19) внутрішньо неузгоджена: RCFC «спіймано 1, вижило 1» із 3; pipeline «2 + 0» із 3;
- у pipeline стоїть **PASS** при 66,7 %.

Потрібно:
- (а) шукати ціль регулярним виразом, нечутливим до пробілів, або брати рядок з RTL;
- (б) показувати `NOT_APPLIED` окремою колонкою;
- (в) `NOT_APPLIED` > 0 має бути помилкою прогону, а не результатом.

**З3. Чому вижили мутанти арбітра: тест тавтологічний.**

Це найважливіша знахідка експерименту, але звіт її не пояснює. У `km_cascade_arbiter_engine.sv` (стани `ST_TC05_*`, рядки ≈ 233–270) самоперевірка порівнює **вираз**, а не записаний регістр:

```verilog
int8_val_q <= int8_val_q + 8'sd1;               // мутант змінює це
if (int8_val_q + 8'sd1 == -8'sd128) ok <= 1;    // а перевіряється це
...
strb_word_q[15:8] <= 8'h55;                     // мутант: 8'hAA
if ({strb_word_q[31:16], 8'h55, strb_word_q[7:0]} == 32'hAABB55DD) // константа, не регістр
```

Перевірка не читає результат присвоєння, тому жодна мутація цього присвоєння не може змінити `pass`. По суті TC-05 перевіряє, що симулятор уміє додавати 8-бітні числа, а не поведінку апаратного регістра. Тестбенч для TC-05 дивиться лише на `tc05_pass` (рядок 67), без `res0` і `res1`.

Наслідок для доказовості: усі раніше заявлені PASS для TC-05 (симуляція і HIL) **не є доказом** обробки переповнення й байтового строба. Вони лише підтверджують, що FSM дійшов до стану FINISH.

Потрібно:
- перевіряти значення регістрів на наступному такті;
- або виводити `int8_val_q`, `u8_val_q`, `strb_word_q` у `res*` і порівнювати їх у тестбенчі з незалежно обчисленими очікуваннями.

**З4. `MUT-RCFC-01` (Fallback → IDLE) вижив.**

Тестбенч RCFC не розрізняє стан слота «Fallback» і «IDLE». Це збігається з висновком AV-08 (S3) і з кодом `km_rcfc_engine.sv`, рядки 46–61 і 166–168: FSM використовує лише слоти 0–2, а стан слота назовні не перевіряється. Порт `slot_state_o` у модулі є, але тестбенч його не перевіряє. Потрібна перевірка `slot_state_o == SLOT_FALLBACK` після сценарію деградації (стан `slot_state_q[0] <= SLOT_FALLBACK`, рядок 335).

## 3. Другорядні зауваження

- Мутанти — це 3–4 ручні правки на модуль. Їх обрав той самий агент, що оцінює результат. Систематичних операторів мутацій (інверсія умов, `<`↔`<=`, константа ±1, вимкнення гілки) немає, тож 80 % не можна порівнювати з іншими проєктами. Рекомендація: генерувати мутанти автоматично за операторами, а ручні лишити як додаткові.
- Шлюз: мутанти `MUT-GATE-01..04` (AV-07) не збігаються з 8 мутантами AV-04. Разом вони покривають більше, але таблицю відповідності варто дати в одному місці.
- `KILLED` через `COMPILATION_ERROR` і `TIMEOUT` слід рахувати окремо. Мутант, що не компілюється, нічого не каже про тестбенч. У цьому прогоні 2 таймаути (`EUCLID-01/02`) і 0 помилок компіляції.
- Критерій «рядок `FAIL` у виводі» крихкий: його можна випадково спрацювати текстом `$display`. Надійніше орієнтуватися на код повернення `$fatal` або `$finish(1)`.
- Сирий JSON містить абсолютні шляхи `/home/<user>/...` у полі `detail`. У звіті є посилання `file:///…`.
- Немає походження: коміт RTL, версія iverilog, SHA-256 файлів. Правило §2, п. 5.
