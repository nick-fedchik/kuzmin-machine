## 2. Властивості

`p_*` — значення входу або стану на попередньому фронті. Перевірка активна, якщо скидання не було ні в попередньому, ні в поточному такті.

| ID | Твердження (assert) | Відповідає |
| :--- | :--- | :--- |
| `P1_commit_iff` | `committed == event_valid ∧ cand_known ∧ assum_known ∧ assum_true ∧ inv_known ∧ inv_true` | P1 плану |
| `P2_exclusive` | `¬(committed ∧ rejected)` | P2 |
| `P2_exactly_one` | `committed ∨ rejected == event_valid` | P2 |
| `P2_reason_input`, `P2_reason_inv`, `P2_reason_or` | Причина відмови однозначна, і `rejected = rej_input ∨ rej_invariant` | P2 (уточнення) |
| `P3_hold`, `P3_take` | `state` змінюється лише на commit і тоді дорівнює кандидату | P3 |
| `P3_changed` | `changed == committed ∧ candidate ≠ state_попередній` | P3 (уточнення) |
| `P4_reset_state`, `P4_reset_flags` | Під час скидання й у такті після нього `state = RESET_VALUE` і всі прапорці дорівнюють 0. RESET_VALUE ненульове, тож помилку «скидання в 0» видно | P4 |
| `P5_unknown`, `P5_observed` | `unknown_hazard == event_valid ∧ ¬hazard_known`; `hazard_observed == event_valid ∧ hazard_known ∧ hazard_true` | P5 |
| `PX_hazard_blocks` | `¬(committed ∧ hazard_known ∧ hazard_true)` — вимога POL Spec, рядки 75, 94 | Окремий прогін, лише щоб задокументувати конфлікт специфікацій |

## 5. Конфлікт специфікацій щодо hazard — формальне підтвердження

`PX_hazard_blocks` дає **FAILED** для обох ширин і обох розв'язувачів (`raw/av04_formal/origPOL_W*.bmc.vcd`). Тобто існує допустима послідовність входів, за якої `hazard_known = 1`, `hazard_true = 1`, а шлюз робить commit. Cover-ціль `C_commit_hazard` досяжна й на основному прогоні.

Як це оцінювати:
- Це **не помилка RTL відносно KPOL Draft v0.1**: там hazard лише позначається прапорцем.
- Але це **пряме порушення** формулювання «апаратно заборонено» у Problem-Oriented Language Specification (рядки 75, 94).
- Рішення має ухвалити автор моделі: або змінити RTL і додати P6 «hazard блокує commit», або виправити POL Spec.
- Поки рішення немає, твердження «hazard апаратно заборонено» в будь-яких матеріалах **неправдиве**.

## 6. `kuzmin_sva_checker.sv` — результат перевірки придатності

Доказ: `raw/av04_sva_checker_probe.txt`.

1. **Немає об'єкта перевірки.** Жоден із 13 портів чекера (`ev_vec`, `commit_we`, `post_phase_enqueued`, `dot_flag_false`, `is_undef_in`, `slot_state` …) не існує в `02-engineering-hardware/rtl/`. Модуля `kuzmin_event_evaluator`, на який посилається коментар, теж немає. Чекер ніде не інстанційовано й не прив'язано через `bind`.
2. **Модель слотів не збігається з реальною.**
   - Чекер: `slot_state[NUM_SLOTS]` по 2 біти (0 — IDLE, 1 — DISPATCHED, 2 — DONE, 3 — WAITING).
   - `km_rcfc_engine.sv`: 3 біти й інші стани (IDLE, DISPATCHED, RUNNING, READY, FALLBACK, TIMEOUT). Назовні видно лише стан вибраного слота (`slot_state_o`).
3. **Відкриті інструменти не приймають файл.**
   - Yosys 0.52 зупиняється на рядку 35 (unpacked-масив у порту).
   - Конкурентні SVA (`default clocking`, `disable iff`, `##[1:N]`) потребують комерційного фронтенду (Verific / Tabby CAD).
4. **«Чистий lint Verilator» нічого не доводить для `a_slot_live`.** Рядки 84–95 стоять під `` `ifndef VERILATOR ``, тож Verilator їх навіть не компілює.

Висновок: п'ять «SVA-властивостей» чекера на сьогодні **не перевірено ні формально, ні в симуляції**. У звітах їх не можна подавати як верифіковані.

## 7. Межі чинності (що цей результат НЕ доводить)

- **Двозначна логіка.** Формальна модель не має X/Z. Перевірки `===`/`!==` у RTL вироджуються в `==`, а гілка `hazard_true_i !== 0 && !== 1` недосяжна. Поведінку з X перевіряє лише симуляція (AV-07 / тестбенчі).
- **Скидання синхронне в моделі** (`async2sync`). Метастабільність і час зняття скидання не перевірено.
- **Обсяг.** Перевірено лише ядро `kpol_txn_gate`. Не перевірено:
  - обгортку `kpol_txn_gate_axi_lite.sv` (протокол AXI-Lite, регістрова карта);
  - верхній рівень `kpol_txn_gate_pynq_z1_top.v`;
  - інші модулі `km_*`.
- **RTL ≠ бітстрім.** Еквівалентність синтезованого нетлиста й RTL не перевіряли.
- **Властивості — переклад тексту плану.** Сам план узгоджено з KPOL Draft v0.1. Якщо KPOL зміниться, властивості потрібно переглянути.

## 8. Вплив на рівень доказовості

- Для **компонента шлюзу** це найсильніший доказ у репозиторії: доведено необмежену коректність щодо записаної специфікації, а не лише проходження прикладів.
- Рівень технології МК загалом **не змінюється**:
  - немає генератора KPOL→RTL;
  - інші модулі не мають формальних властивостей;
  - SVA-чекер не застосовний.
